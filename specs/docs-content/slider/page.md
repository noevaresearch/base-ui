## Prose claims about component behavior

Each claim below is what the page text says, cross-checked against the behavior spec.

- Accessibility guideline: "Form controls must have an accessible name" — prefer `<Slider.Label>`, or provide an `aria-label` on each `<Slider.Thumb>` when no visible label is rendered (`docs/src/app/(docs)/react/components/slider/page.mdx:15`). Consistent with behavior spec § Accessibility (label linking via `aria-labelledby`, forwarded thumb `aria-label`, `getAriaLabel`).
- Anatomy: "Import the component and assemble its parts" — the snippet imports `Slider` from `@base-ui/react/slider` and composes `Slider.Root` > `Slider.Label` + `Slider.Value` + `Slider.Control` > `Slider.Track` > `Slider.Indicator` + `Slider.Thumb` (`docs/src/app/(docs)/react/components/slider/page.mdx:19-34`). This composition matches behavior spec § DOM structure & portal behavior (Root/Control/Track/Indicator/Label divs, Value `<output>`, Indicator + Thumb inside Track).
- Labeling: a single-thumb slider without a visible label (such as a volume control) can be labeled with `aria-label` on `<Slider.Thumb>` (`docs/src/app/(docs)/react/components/slider/page.mdx:40`); a visible label is created with `<Slider.Label>` (`docs/src/app/(docs)/react/components/slider/page.mdx:54`); a multi-thumb range slider with a visible label should add `aria-label` on each `<Slider.Thumb>` to distinguish them (`docs/src/app/(docs)/react/components/slider/page.mdx:69`). Consistent with behavior spec § Accessibility and § Focus management (label click focuses the registered thumb; for range sliders label click focuses no thumb — the page does not contradict this).
- Range slider recipe: (1) pass an array of values and place one `<Slider.Thumb>` per value in the array; (2) for server-side rendering, specify a numeric `index` for each thumb corresponding to its value's index (`docs/src/app/(docs)/react/components/slider/page.mdx:88-91`). Consistent with behavior spec § State model (range creation) and § Public API surface (`index` prop).
- Thumb collision: thumbs can be configured to behave differently when they collide during pointer interactions via the `thumbCollisionBehavior` prop on `<Slider.Root>` (`docs/src/app/(docs)/react/components/slider/page.mdx:93`). Consistent with behavior spec § Events (none/push/swap collision semantics) and § Public API surface.
- Steps: `step` snaps the value to multiples of a given increment; `largeStep` controls the increment for Page Up/Page Down or Shift + Arrow Up/Arrow Down (`docs/src/app/(docs)/react/components/slider/page.mdx:101`). Consistent with behavior spec § Keyboard interactions.
- Marks: render your own tick marks, positioning each mark along the track as a percentage of the value range (`docs/src/app/(docs)/react/components/slider/page.mdx:109`); "Marks are independent of the value's granularity" — pair them with the `step` prop to snap the thumb to each mark (`docs/src/app/(docs)/react/components/slider/page.mdx:115`). Not covered by the behavior spec (marks are user-rendered elements; no slider part or test governs them) — flagged in Discrepancies.
- Thumb alignment: `thumbAlignment="edge"` insets the thumb so its edge aligns with the control edge when the value is at `min` or `max`, "without overflowing the control like the default `"center"` alignment" (`docs/src/app/(docs)/react/components/slider/page.mdx:119`); `thumbAlignment="edge-client-only"` is a client-only alternative that "can be used to reduce bundle size but only renders after React hydration" (`docs/src/app/(docs)/react/components/slider/page.mdx:121`). The prop values match behavior spec § Public API surface; the edge visibility/measurement mechanics match behavior spec § DOM structure & portal behavior. The hydration-timing and bundle-size rationale for `edge-client-only` is a docs-only claim (behavior spec § Edge cases only exercises its press-value mapping) — flagged in Discrepancies.
- Vertical: set `orientation="vertical"` on `<Slider.Root>` to build a vertical slider (`docs/src/app/(docs)/react/components/slider/page.mdx:129`). Consistent with behavior spec § State model (orientation default/alternate) and § Accessibility (`aria-orientation`).
- Form integration: to use a slider in a form, pass the slider `name` to `<Slider.Root>` (`docs/src/app/(docs)/react/components/slider/page.mdx:137`). Consistent with behavior spec § Edge cases (value(s) included in FormData on submit) and § Public API surface (`name`).
- Fieldset composition: for grouped multi-thumb range sliders in forms, Fieldset can provide the shared visible label (via `Fieldset.Legend` around `Fieldset.Root render={<Slider.Root .../>}`) while each thumb keeps its own `aria-label` (`docs/src/app/(docs)/react/components/slider/page.mdx:154-173`). Not covered by the behavior spec (§ Edge cases covers Form/Field, not Fieldset) — flagged in Discrepancies.

## Discrepancies (docs page vs. behavior.md)

No direct contradictions between page prose and the behavior spec were found. Flags:

- Docs-only claims with no behavior-spec coverage (not contradicted, just unproven by the unit's own tests):
  - Marks positioning as a percentage of the value range, and "Marks are independent of the value's granularity" (`docs/src/app/(docs)/react/components/slider/page.mdx:109`, `docs/src/app/(docs)/react/components/slider/page.mdx:115`) — the behavior spec has no marks-related behavior (marks are user-rendered elements).
  - `thumbAlignment="edge-client-only"` rendering "only after React hydration" and the bundle-size rationale (`docs/src/app/(docs)/react/components/slider/page.mdx:121`) — behavior spec § DOM structure & portal behavior covers the `edge` visibility gating and SSR script, and § Edge cases only covers `edge-client-only` press-value mapping; hydration timing/bundle size is asserted nowhere in the behavior spec.
  - Fieldset composition guidance (`docs/src/app/(docs)/react/components/slider/page.mdx:154-173`) — behavior spec § Edge cases covers Form/Field integration but has no Fieldset tests.
- Apparent notational mismatch in the rendered API reference: `Root.ChangeEventReason`/`Root.CommitEventReason` list the reason strings as `'input-change' | 'track-press' | 'drag' | 'keyboard' | 'none'` (`docs/src/app/(docs)/react/components/slider/types.md:96-100`, `docs/src/app/(docs)/react/components/slider/types.md:127-131`), while behavior spec § Events cites tests via `REASONS` constant property names (`trackPress`, `inputChange`) without spelling out the constants' string values — likely constant-name vs. string-value notation rather than a substantive conflict.
- Defaults the rendered API reference presents that behavior spec § State model explicitly marks UNVERIFIED: `largeStep` default `10` (`docs/src/app/(docs)/react/components/slider/types.md:26`) and `minStepsBetweenValues` default `0` (`docs/src/app/(docs)/react/components/slider/types.md:27`); `thumbCollisionBehavior` default `'push'` (`docs/src/app/(docs)/react/components/slider/types.md:24`) is likewise not asserted anywhere in the behavior spec. (`step` default `1` and `orientation` default `'horizontal'` are consistent with behavior spec § State model.)
