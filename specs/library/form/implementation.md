# `Form` — implementation spec (mined from source)

Unit: `form` (library). Source files: `packages/react/src/form/Form.tsx`, `packages/react/src/form/Form.spec.tsx`, `packages/react/src/form/index.ts`.
Ground truth for WHAT happens: `specs/library/form/behavior.md` (cited by section name below). This file explains WHY/HOW the source produces it. Form.tsx is deliberately thin (251 lines): it owns only the submit orchestration, the error mirror, and the field registry handle — all per-field state lives in the `Field` package, which pulls Form's refs down through context and pushes validity back up into the registry.

## State machine / hooks used

Form has no internal state machine of its own; it is a passive registry holder plus a submit orchestrator. The "state" is distributed:

- **The field registry** — `formRef` is a plain `React.useRef` holding `{ fields: Map<string, RegistryEntry> }` `packages/react/src/form/Form.tsx:36-38`. It is a ref, not state, on purpose: field mount/unmount and validity updates must never re-render the `<form>` (only children re-render when their own validity state changes). The registry is the single source of truth for three submit-time decisions: gating, focus targeting, and value projection (see the Events section of behavior.md). Form never writes entries itself; consumers do (see Context section).
- **Error mirror** — `errors` is "controlled with an internal mirror": `React.useState(externalErrors)` seeds local state from the prop `packages/react/src/form/Form.tsx:73`, `useValueChanged(externalErrors, ...)` re-syncs it when the prop identity changes `packages/react/src/form/Form.tsx:75-77`, and `clearErrors` is the only local writer `packages/react/src/form/Form.tsx:145-157`. This mirrors-without-`useControlled` pattern exists because the `errors` record is externally owned but must be locally prunable: there is no `onErrorsChange` callback, so when a field's value changes and the corresponding external error must disappear (State model section of behavior.md), Form can only honor that by deleting the key from a local copy. `clearErrors` is a no-op re-render-wise when the key is absent (early return of `previousErrors`) and uses `Object.hasOwn` so prototype-less error objects (the `Object.create(null)` case in behavior.md's State model section) are handled `packages/react/src/form/Form.tsx:149-156`. The mirror is published via context as `errors ?? EMPTY_OBJECT` for referential stability `packages/react/src/form/Form.tsx:164`.
- **`useValueChanged`** (`packages/react/src/internals/useValueChanged.ts:6-16`) — diff-on-`Object.is` + `useIsoLayoutEffect`; Form's only sync mechanism from prop → local state. Note it can only observe prop *identity* changes; in-place mutation of the errors record by the consumer would not sync (no test covers that; the `Object.create(null)` test in behavior.md's State model section updates immutably).
- **`submittedRef` + post-submit effect** — the focus-on-invalid-submit behavior is split across two phases. In the submit handler, `focusFirstInvalid()` runs synchronously and focuses field-validator failures immediately `packages/react/src/form/Form.tsx:119`. For errors that arrive *after* submit (async server errors — Events section of behavior.md), `submittedRef` is set to `true` right before `onSubmit` fires `packages/react/src/form/Form.tsx:124`, and a `React.useEffect` keyed on `[errors, focusFirstInvalid]` consumes the flag exactly once: it runs `focusFirstInvalid()` when the errors mirror commits post-submit, then resets the flag `packages/react/src/form/Form.tsx:79-86`. This is what makes external-error focus happen "only on submit, never on value change" (Focus management section of behavior.md): a later `errors` prop change without an intervening submit finds `submittedRef === false` and does nothing.
- **`focusFirstInvalid`** (`useStableCallback`, `packages/react/src/form/Form.tsx:43-71`) — iterates the registry in insertion order, and among invalid fields picks the control that comes first by *document position*, not registration order, via `comesBeforeInSameTree` `packages/react/src/form/Form.tsx:244-251` (`compareDocumentPosition` with the `DOCUMENT_POSITION_DISCONNECTED` bit masked out). That mask is the disconnected-shadow-root fallback: controls in different disconnected trees are not orderable, so among them registration (insertion) order wins — the behavior pinned by the portal/shadow-root tests in behavior.md's Focus management section. Returns a tri-state-ish boolean: `true` if it focused something, otherwise `hasInvalid` — so submission is blocked even when *no* invalid field has a usable control `packages/react/src/form/Form.tsx:63-70` (the checkbox-group-with-no-controls case in the comment at `packages/react/src/form/Form.tsx:44-46`). `select()` is applied only when the control `tagName === 'INPUT'` `packages/react/src/form/Form.tsx:65-67`.
- **`submitCountRef`** — bumped on every submit attempt, valid or not `packages/react/src/form/Form.tsx:112`, and shared via context. It is Form's "a submit happened" broadcast: consumers gate behavior on it (see Context section).
- **`React.useImperativeHandle(actionsRef, ..., [])`** with an empty dep array `packages/react/src/form/Form.tsx:88-104` — the handle is allocated once; `validate(name)` scans the registry by `field.name === fieldName` with `Array.find` (first match) and `validate()` iterates all entries. The closures it calls are the registry entries' own `validate` functions, so the handle stays correct across rename/unmount/replacement (Focus management section of behavior.md) without the handle itself ever re-binding.
- **`useRenderElement('form', ...)`** `packages/react/src/form/Form.tsx:106-143` — the standard Base UI render pipeline: composes `[forwardedRef, elementRef]` and merges the Form-injected props (`noValidate: true`, the submit handler) ahead of `elementProps`, so a user-supplied `noValidate={false}` overrides the default (DOM structure section of behavior.md).
- Notably **absent**: `useControlled` (the errors mirror is hand-rolled, see above), `useIsoLayoutEffect` (Form itself only uses `React.useEffect` at `packages/react/src/form/Form.tsx:79`; layout effects live in the registering children), and any timeout/animation helpers.

The submit pipeline, end to end (`packages/react/src/form/Form.tsx:111-138`): increment `submitCountRef` → run every registered field's `validate()` synchronously → if `focusFirstInvalid()` returns truthy, `preventDefault()` and stop → else set `submittedRef`, call the user's `onSubmit` → if `onFormSubmit` is present: `preventDefault()`, project `{ [name]: field.getValue() }` from the registry (unnamed fields skipped) `packages/react/src/form/Form.tsx:130-135`, and call it with `createGenericEventDetails(REASONS.none, event.nativeEvent)` `packages/react/src/form/Form.tsx:137` (which is why `eventDetails.event.defaultPrevented` is `true` in behavior.md's Events section). Async validators cannot block the submit — `validate()` gives only the *synchronous* verdict back (see Dependencies; the registry entry contract documents this at `packages/react/src/internals/form-context/FormContext.ts:18-22`), and a pending async verdict leaves the field valid until it settles — the source-level reason for the async-race semantics in behavior.md's Edge cases section.

## Context providers/consumers

Form provides `FormContext` (`packages/react/src/form/Form.tsx:171`, value memoized at `packages/react/src/form/Form.tsx:159-169`). The context type is defined *in internals*, not in the form folder: `packages/react/src/internals/form-context/FormContext.ts:9-46`, with a standalone default value (`NOOP` clearErrors, empty map) so Field works without a surrounding Form. Six things cross the boundary:

- `formRef` — the registry handle. Written by the field package (`packages/react/src/internals/field-register-control/useFieldControlRegistration.ts:71-84,105-131` sets entries keyed by the registration's field id in layout effects and deletes on unmount; a control swap deletes the previous id first at `packages/react/src/internals/field-register-control/useFieldControlRegistration.ts:162-164` — that keying-by-instance is the source mechanism behind "same-name fields are scoped per instance" and "last control wins" in behavior.md's State model and Edge cases sections). Read by Form at submit time; also read by `useFieldValidation` to write settled validity back into the entry (`packages/react/src/field/root/useFieldValidation.ts:136-149`) and to project cross-field validator inputs (`packages/react/src/field/root/useFieldValidation.ts:293-298` — the same projection shape Form builds at `packages/react/src/form/Form.tsx:130-135`).
- `errors` (the mirror) — consumed by `FieldRoot` (folds form-level errors into field validity, `packages/react/src/field/root/FieldRoot.tsx:26`) and `FieldError` (renders the message text, `packages/react/src/field/error/FieldError.tsx:39`). Form itself never interprets an error entry.
- `clearErrors` — consumed by `FieldControl` on value change (`packages/react/src/field/control/FieldControl.tsx:112,156`) and independently by every value-owning control: `CheckboxRoot`, `SwitchRoot`, `RadioGroup`, `CheckboxGroup`, `SliderRoot`, `NumberFieldRoot`, `NumberFieldInput`, `SelectRoot`, `OTPFieldRoot`, `AriaCombobox` (all import `useFormContext` for `clearErrors`). This is the mechanism clearing external errors on change (State model section of behavior.md).
- `elementRef` — the `<form>` DOM node, consumed for DOM-association checks: input eligibility (`isEligibleInput` compares `input.form === formElement`, `packages/react/src/field/root/useFieldValidation.ts:32-44`) and the Enter-key implicit-submit check (`event.currentTarget.form === formElementRef.current`, `packages/react/src/field/control/FieldControl.tsx:193`).
- `validationMode` — passed through as a plain value; `FieldRoot` uses it as the default per-field mode (`packages/react/src/field/root/FieldRoot.tsx:26`) while `Field.Root`'s own `validationMode` wins (per the prop's JSDoc at `packages/react/src/form/Form.tsx:194-204`).
- `submitCountRef` — consumed by `FieldRoot` to decide whether `onSubmit`-mode validation state is visible after the first submit (`packages/react/src/field/root/FieldRoot.tsx:90`) and by `FieldControl`'s Enter handler: it snapshots the count and only commits validation on a 0ms fallback timer if Form's submit handler didn't already run and bump it (`packages/react/src/field/control/FieldControl.tsx:195-202`).

Boundary direction to note: data flows *down* as refs and stable callbacks (no reactive values except `errors`/`validationMode`), and *up* only through mutations of those shared refs. Form never re-renders because of its children; children re-render because of their own state and the context `errors` value.

## DOM/portal strategy and why

- Form renders exactly one element — the native `<form>` via `useRenderElement` `packages/react/src/form/Form.tsx:106` — no wrapper, no portal, no hidden inputs. It is intentionally a *participation coordinator*, not a DOM manager: membership is decided by React context, not DOM ancestry, so portaled fields (including into shadow roots) register normally. The only DOM-coupling rules live in `isEligibleInput` (`packages/react/src/field/root/useFieldValidation.ts:32-44`): `:disabled` inputs are excluded, and an explicit `form` attribute pointing elsewhere opts an input out; an unassociated portaled input still participates. That is the source-level explanation for the portal/shadow-root behavior in behavior.md's DOM structure & portal behavior section.
- `elementRef` is shared through context precisely so consumers can do those `form`-attribute ownership checks against the real node without DOM traversal from the field upward.
- The single DOM-order dependence is focus targeting: `comesBeforeInSameTree` `packages/react/src/form/Form.tsx:244-251` uses `compareDocumentPosition` so first-invalid follows the *current* document order after keyed reorders (Focus management section of behavior.md), while disconnected trees degrade to registration order. No scroll-into-view is attempted anywhere — consistent with behavior.md's UNVERIFIED focus note.
- `noValidate: true` is injected as a prop default ahead of `elementProps` in the merge order `packages/react/src/form/Form.tsx:108-142`, which is why the browser's native constraint UI is always suppressed unless the user opts back in with `noValidate={false}` (DOM structure section of behavior.md) — Base UI re-implements gating on top of the registry instead.

## Dependencies on other Base UI internals

Imports from `packages/react/src/form/Form.tsx:3-13`:

- `@base-ui/utils/useStableCallback` (`packages/react/src/form/Form.tsx:3`) — `focusFirstInvalid`, `clearErrors`.
- `@base-ui/utils/empty` (`EMPTY_OBJECT`, `packages/react/src/form/Form.tsx:4`) — stable empty errors default.
- `internals/createBaseUIEventDetails` (`packages/react/src/form/Form.tsx:5-8`) — builds `onFormSubmit`'s event details; `REASONS` from `internals/reasons` (`packages/react/src/form/Form.tsx:9`) supplies the reason value (`REASONS.none`; the only submit reason Form emits, see the re-exported types at `packages/react/src/form/Form.tsx:180-181`).
- `internals/types` (`BaseUIComponentProps`, `packages/react/src/form/Form.tsx:10`) — standard prop plumbing for the rendered element.
- `internals/form-context/FormContext` (`packages/react/src/form/Form.tsx:11`, defined at `packages/react/src/internals/form-context/FormContext.ts`) — the shared contract with the field package. Its registry-entry type embeds `FieldValidityData` from `field/root/FieldRoot` (`packages/react/src/internals/form-context/FormContext.ts:3`), so **form depends on the field package's types** while field depends on form's context — the coupling point is this internals file.
- `internals/useRenderElement` (`packages/react/src/form/Form.tsx:12`) — shared render pipeline (ref composition, props merge).
- `internals/useValueChanged` (`packages/react/src/form/Form.tsx:13`).

Reverse dependencies (consumers of `useFormContext`, from grep): the `field` package (`FieldRoot`, `FieldControl`, `FieldError`, `useFieldValidation`, `useFieldControlRegistration`) plus value-owning controls `Checkbox`, `Switch`, `RadioGroup`, `CheckboxGroup`, `Slider`, `NumberField`, `Select`, `OTPField`, `Combobox` (aria variant). Any port of `form` to another framework must reproduce the `FormContext` contract — registry entry shape (`name`, `validate`, `validityData`, `controlRef`, `getValue`; `packages/react/src/internals/form-context/FormContext.ts:13-27`), the synchronous-verdict guarantee, and `clearErrors`/`submitCountRef` semantics — or all of those controls lose validation and value projection.

Not used by this unit: `floating-ui-react`, `use-render`, portal utilities, and the `form-data` npm package (present in the workspace but not imported here). The `library: form` entry in `TODO.md:401-407` has no `wraps-external:` field, so there is no external-package delegation to record.

## Anything in source not explained by any test

Flagged explicitly — none of these are covered by `packages/react/src/form/Form.test.tsx` per behavior.md:

1. **`actionsRef.validate(name)` with duplicate names** resolves via `Array.find` in registry insertion order `packages/react/src/form/Form.tsx:92-95`, so only the *first-registered* field with that name is re-validated. behavior.md's State model section proves per-instance scoping for submit/`aria-invalid`, and its Focus management section proves `validate(name)` targeting across rename/unmount/replace — but never with two same-named fields simultaneously.
2. **Valid submit without `onFormSubmit` does not `preventDefault`** — the native default (actual form submission/navigation in a browser) proceeds; Form only prevents default when invalid (`packages/react/src/form/Form.tsx:119-121`) or when `onFormSubmit` exists (`packages/react/src/form/Form.tsx:127-128`). Tests always call `preventDefault()` in their own `onSubmit` (behavior.md's Events section), so the bare native-submission path is unpinned.
3. **Blocked submission with no focusable control** — `focusFirstInvalid` returns `hasInvalid` when no invalid field has a usable control `packages/react/src/form/Form.tsx:63-70`, keeping submit gated without moving focus. behavior.md's UNVERIFIED focus note covers fields beyond the first; this stronger claim (blocking with *zero* focusable controls, e.g. the comment's checkbox-group case at `packages/react/src/form/Form.tsx:44-46`) has no test either.
4. **`select()` applied to any `<INPUT>` tag**, not just text inputs `packages/react/src/form/Form.tsx:65-67` — behavior.md's Focus management section only proves it for a text input (`select()` called exactly once).
5. **One-shot post-submit focus** — the effect resets `submittedRef` after its first run `packages/react/src/form/Form.tsx:79-86`, so only the *first* `errors` change after a submit triggers focus; subsequent error updates never re-focus until another submit. behavior.md's Focus management section pins "focus on submit, not on change" and the second-submission case, but not the multi-error-update-after-one-submit sequence.
6. **In-place mutation of the `errors` prop** is not observed (the mirror syncs on `Object.is` identity via `useValueChanged`, `packages/react/src/form/Form.tsx:75-77` / `packages/react/src/internals/useValueChanged.ts:10-16`); the prototype-less-errors test in behavior.md's State model section updates immutably, so nothing pins what happens if a consumer mutates the record in place.
7. **`Form.spec.tsx` is a type-only file, not a runtime test**: it pins generic `FormValues` inference on `onFormSubmit` (`values.name: string`, `values.age: number`, unknown keys rejected) and native `<form>` prop exposure in the `render` callback (`noValidate`) with `expectType` assertions `packages/react/src/form/Form.spec.tsx:10-25`. These compile-time contracts have no runtime equivalent in the test suite.
