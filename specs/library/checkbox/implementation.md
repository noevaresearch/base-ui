# Checkbox — implementation spec (Stage 2: implementation mining)

Unit: `checkbox` (`packages/react/src/checkbox`). Companion to the Stage 1 document `specs/library/checkbox/behavior.md`, which is ground truth for WHAT the component does; this document explains the state machine, hook composition, context wiring, and DOM decisions that produce that behavior. Where this document needs to refer back to a tested claim, it cites behavior.md by section name instead of re-describing it.

The `TODO.md` entry for `library: checkbox` declares no `wraps-external:` field, so there is no external-package delegation to document: everything below is derived from this unit's own non-test source. All backtick citations point at the eight source files listed for this unit.

## State machine / hooks used

The component has no reducer. Its "state machine" is a single controlled boolean (`checked`) plus a render-only flag (`indeterminate`), wrapped in hooks that each own one concern; the Field lifecycle state (touched/dirty/filled/focused/valid) is not owned here at all — it is inherited from `FieldRootContext` (see next section).

Hooks and their call sites (in `packages/react/src/checkbox/root/CheckboxRoot.tsx` unless noted):

- `useControlled` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:137-145`) — the one source of truth for `checked`. Uncontrolled mode stores the boolean internally with `defaultChecked` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:142`); controlled mode receives either group membership (`groupValue.includes(value)`) when the checkbox participates in a `CheckboxGroup` via `value`, or `groupChecked` — the `checked`-like value handed down by a parent checkbox (`packages/react/src/checkbox/root/CheckboxRoot.tsx:138-141`, with the group prop splicing at `packages/react/src/checkbox/root/CheckboxRoot.tsx:119-124`). `setCheckedState` is called from exactly one place, the hidden input's `onChange` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:237`): every user interaction funnels through a single native change event (see DOM strategy).
- Vetoable change protocol — `onCheckedChange` and `groupOnChange` are invoked with `createChangeEventDetails(REASONS.none, event.nativeEvent)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:223`), and `details.isCanceled` short-circuits before the state update and before the group update, in that order (`packages/react/src/checkbox/root/CheckboxRoot.tsx:227-229`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:231-235`). This two-consumer, two-veto-point chain is the mechanism behind behavior.md → "State model (controlled/uncontrolled, defaults, transitions)" (`cancel()` leaves both `aria-checked` and the input unchanged).
- `useButton` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:130-133`) — supplies `getButtonProps`/`buttonRef` and centralizes the native-vs-non-native button duality: with the default `nativeButton = false` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:68`) the visible `span` gets non-native button props; with `nativeButton` + `render={<button/>}` it becomes a real button. The shared button layer is why behavior.md → "Keyboard interactions" (Space toggles, Enter must be suppressed) and the `render`/`role="switch"` conformance come almost for free.
- `useIsoLayoutEffect` #1 (`packages/react/src/checkbox/root/CheckboxRoot.tsx:173-182`) — re-asserts `inputRef.current.indeterminate = computedIndeterminate` on every `checked`/`indeterminate` change (`packages/react/src/checkbox/root/CheckboxRoot.tsx:176`), because a native click resets the DOM property; this is the WHY behind behavior.md → "State model" (clicking while indeterminate keeps the input indeterminate while `checked` advances). The same effect pushes `setFilled(checked)` into the Field when not grouped (`packages/react/src/checkbox/root/CheckboxRoot.tsx:179-181`).
- `useValueChanged` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:184-193`) — fires only on actual `checked` changes (not mount): `clearErrors(name)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:189`), `setDirty(checked !== validityData.initialValue)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:190`), and `validation.change(checked)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:192`). This produces behavior.md → "State model" (`data-dirty`, one validation run per user change, re-validation on externally driven controlled changes). Both effects early-return inside groups (`packages/react/src/checkbox/root/CheckboxRoot.tsx:185-187`), because the group owns filled/dirty/validation for its members.
- `useIsoLayoutEffect` #2 (`packages/react/src/checkbox/root/CheckboxRoot.tsx:391-397`) — registers a child checkbox's rendered element id with a parent checkbox via `parentContext.registerChildId(value, renderedId)`; the parent aggregates these into `aria-controls` (behavior.md → "Accessibility (roles, aria-*, id linking)").
- `React.useEffect` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:265-276`) — publishes each child's `disabled` into the parent's `disabledStatesRef`, keyed by `value`, and cleans up on unmount/disabled-change.
- `useRegisterFieldControl(controlRef, id, checked, ...)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:152`) — registers the visible control with the Field (gated on `!groupContext && !disabled`, so groups and disabled checkboxes do not register), passing the current `checked`.
- `useMergedRefs` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:164`) — combines the consumer's `inputRef`, the internal `inputRef`, and validation input registration (skipped entirely for `parent` checkboxes).
- `useBaseUiId` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:98`) — per-instance generated id for the visible element in non-native mode (`rootId`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:108`). The SSR-deferral and keyed-remount id guarantees in behavior.md → "Accessibility" are delegated to this hook and to `useLabelableId`.
- `useLabelableId({ id: idProp || undefined, enabled: ownsControlId })` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:106`) — resolves the labelable control id; the `|| undefined` (per the inline comment at `packages/react/src/checkbox/root/CheckboxRoot.tsx:105`) is what makes an empty `id=""` fall back to the Field's control id. `ownsControlId` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:103`) suppresses id ownership for checkboxes that share a `CheckboxGroup`'s labelable scope (the group itself is the Field's control — see the comment at `packages/react/src/checkbox/root/CheckboxRoot.tsx:100-102`).
- `useAriaLabelledBy(ariaLabelledByProp, labelId, inputRef, !nativeButton, controlId)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:165-171`) — merges the consumer's `aria-labelledby`, the Field label id, and the sibling-label fallback, which is where behavior.md → "Accessibility" `aria-labelledby` claims come from.
- Context consumers `useFormContext`/`useFieldRootContext`/`useFieldItemContext`/`useLabelableContext`/`useCheckboxGroupContext` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:73`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:74-85`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:86`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:87`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:89`) — detailed in the next section.
- Indicator hooks (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx`): `useCheckboxRootContext` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:25`); `useTransitionStatus(rendered)` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:29`) where `rendered = rootState.checked || rootState.indeterminate` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:27`) — the mount predicate explains behavior.md → "DOM structure & portal behavior" (mounted when checked or indeterminate); and `useOpenChangeComplete({ batch: true, enabled: !rendered, open: rendered, ... })` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:38-48`) which defers `setMounted(false)` until exit animation completes — `batch: true` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:39`) is precisely the mechanism behind behavior.md → "Edge cases (rapid interactions, unmount, nesting)" (many simultaneously unchecked indicators removed in one React commit). `shouldRender = keepMounted || mounted` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:57`) gates the early `return null` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:66-68`).

State derivation order (why composition rather than a machine):

1. Merge `disabled` from four sources — prop, `Field.Root`, `Field.Item`, group (`packages/react/src/checkbox/root/CheckboxRoot.tsx:93-94`) — and resolve `name` (Field name wins) and `value` (falls back to `name`) (`packages/react/src/checkbox/root/CheckboxRoot.tsx:95-96`).
2. If grouped under a parent checkbox, pull `parentContext.getParentProps()` or `parentContext.getChildProps(value)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:110-117`), then let the group override `checked`/`indeterminate`/`onCheckedChange` with defaults pointing back at the local props (`packages/react/src/checkbox/root/CheckboxRoot.tsx:119-124`). Group-level `validation` similarly overrides the Field's (`packages/react/src/checkbox/root/CheckboxRoot.tsx:135`).
3. `useControlled` resolves the boolean; `computedChecked`/`computedIndeterminate` fold the parent group's state in (`packages/react/src/checkbox/root/CheckboxRoot.tsx:147-150`).
4. One memoized `state` object spreads `fieldState` plus the checkbox's own keys (`packages/react/src/checkbox/root/CheckboxRoot.tsx:278-288`). This single object is both the context value and the input to the data-attribute mapping (`packages/react/src/checkbox/root/CheckboxRoot.tsx:290`), which is why Root and Indicator always agree on style hooks.

Derived, not stored: `aria-checked` is computed at render as `computedIndeterminate ? 'mixed' : computedChecked` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:299`) — the structural reason behavior.md → "State model" records that `indeterminate` wins over `checked` and is never consumed by clicking (the flag is a prop mirror, not a state bit: the toggle path only ever flips `checked`).

## Context providers/consumers

**Provided:** `CheckboxRootContext` wraps the rendered element and both hidden inputs (`packages/react/src/checkbox/root/CheckboxRoot.tsx:399-406`). The context type is nothing more than the state snapshot (`packages/react/src/checkbox/root/CheckboxRootContext.ts:5-7`) — read-only derived state, no setters or refs — so consumers can react to state but cannot mutate it; all mutation flows back through the root's own event handlers. The only in-repo consumer is `CheckboxIndicator` via `useCheckboxRootContext` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:25`), which throws the "Base UI: CheckboxRootContext is missing…" error when used outside a Root (`packages/react/src/checkbox/root/CheckboxRootContext.ts:9-18`) — the error asserted in behavior.md → "Edge cases". The Indicator spreads `rootState` into its own state and adds `transitionStatus` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:33-36`), then reuses the same checkbox attribute mapping merged with `transitionStatusMapping` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:50-55`): the "state data attributes mirrored onto both Root and Indicator" claim in behavior.md → "DOM structure & portal behavior" is structural (shared state object + shared mapping), not duplicated logic. The mapping itself (`packages/react/src/checkbox/utils/getCheckboxStateAttributesMapping.ts:6-24`) customizes only `checked` — emitting `data-checked`/`data-unchecked` as a mutually exclusive pair and emitting neither while `indeterminate` (whose `data-indeterminate` comes from the generic state machinery instead, per the comment at `packages/react/src/checkbox/utils/getCheckboxStateAttributesMapping.ts:12`) — and appends `fieldValidityMapping` for `data-valid`/`data-invalid` (`packages/react/src/checkbox/utils/getCheckboxStateAttributesMapping.ts:22`). Attribute constants live in `packages/react/src/checkbox/root/CheckboxRootDataAttributes.ts:4-48` and, with the animation hooks added, in `packages/react/src/checkbox/indicator/CheckboxIndicatorDataAttributes.ts:6-34`.

**Consumed** (this is where all Field/Form/Group integration lives — Root composes, never reimplements):

- `FormContext` → `clearErrors` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:73`): checked-value changes clear the field's errors (invoked from `useValueChanged`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:189`) — behavior.md → "Accessibility" (errors cleared on change).
- `FieldRootContext` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:74-85`): Field `disabled`/`name`, the lifecycle setters (`setDirty`/`setFilled`/`setFocused`/`setTouched`), `state` (spread into the component state at `packages/react/src/checkbox/root/CheckboxRoot.tsx:280` — the origin of every `data-touched`/`data-dirty`/`data-filled`/`data-focused`/`data-valid` hook in behavior.md → "State model"), `validationMode`, `validityData`, and `validation`.
- `FieldItemContext` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:86`): adds a `disabled` scope (`packages/react/src/checkbox/root/CheckboxRoot.tsx:94`).
- `LabelableContext` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:87`): `labelId`, `registerControlId`, and `getDescriptionProps` (merged into both the input props and the element props, `packages/react/src/checkbox/root/CheckboxRoot.tsx:261` and `packages/react/src/checkbox/root/CheckboxRoot.tsx:383`) — drives label-`for` linking and `aria-describedby` merging (behavior.md → "Accessibility").
- `CheckboxGroupContext` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:89`): group `value`/`setValue` (updated additively on toggle, `packages/react/src/checkbox/root/CheckboxRoot.tsx:239-245`), the `parent` descriptor (`getParentProps`/`getChildProps`/`registerChildId`/`disabledStatesRef`), and group-level `disabled`/`validation`. `parentContext` is only recognized when the group actually exposes `allValues` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:90-91`).

## DOM/portal strategy and why

No portals exist anywhere in the unit; all DOM renders inline (consistent with behavior.md → "DOM structure & portal behavior", which records no portal assertions). The Root returns three siblings inside the provider (`packages/react/src/checkbox/root/CheckboxRoot.tsx:399-406`):

1. The visible styled element from `useRenderElement('span', …)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:292-387`) with `role="checkbox"`, the aria attributes, and the `data-parent` marker for group-parent checkboxes (`packages/react/src/checkbox/root/CheckboxRoot.tsx:297-303`). Refs merge the button ref, the control ref used for focus forwarding/registration, and the forwarded ref (`packages/react/src/checkbox/root/CheckboxRoot.tsx:294`).
2. An optional `<input type="hidden">` carrying `uncheckedValue` while unchecked (`packages/react/src/checkbox/root/CheckboxRoot.tsx:402-404`). Its condition encodes the submission rules: `!checked` keeps native semantics (unchecked inputs submit nothing), `!groupContext` defers to the group's own submission, `name && !parent` excludes nameless boxes and group parents, and mirroring `disabled` onto it (`packages/react/src/checkbox/root/CheckboxRoot.tsx:403`) is what withholds `uncheckedValue` for disabled boxes (behavior.md → "Events (names, payload shape, bubbling, preventDefault semantics)").
3. The visually hidden native `<input type="checkbox">` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:405`, props at `packages/react/src/checkbox/root/CheckboxRoot.tsx:195-263`): `name`/`form`/`required`/`checked`, `tabIndex: -1`, `aria-hidden: true`, `id = nativeButton ? undefined : controlId` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:204`), `name: parent ? undefined : name` to exclude parents from submission (`packages/react/src/checkbox/root/CheckboxRoot.tsx:201`), and `style: name ? visuallyHiddenInput : visuallyHidden` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:207`). `suppressHydrationWarning` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:405`) tolerates server/client mismatch on a browser-managed input (`checked` is property-driven and `indeterminate` has no attribute form).

Why this split:

- **The native input is the form engine.** FormData participation, native `required`/`valueMissing` validation, external-form association via `form`, and the browser's own toggle behavior are inherited rather than reimplemented — the WHY behind behavior.md → "Events" (submission values follow native checkbox semantics) and → "Accessibility" (native validation preserved).
- **The visible control is the a11y/focus surface.** It is the only tabbable, labelled, role-carrying element; the input is `aria-hidden` and untabbable, and its `onFocus` forwards focus to the visible control (`packages/react/src/checkbox/root/CheckboxRoot.tsx:252-254`) so label-driven focus lands on the styled element.
- **Toggling re-dispatches a click onto the input instead of setting state directly.** The root's `onClick` bails for `readOnly`/`disabled` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:366`), calls `event.preventDefault()` on the original click (`packages/react/src/checkbox/root/CheckboxRoot.tsx:370`), then `dispatchClickWithModifiers(input, event)` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:377`). The browser then performs a real toggle+change on the input, whose `onChange` is the single transition funnel (`packages/react/src/checkbox/root/CheckboxRoot.tsx:211-246`). Two consequences documented in behavior.md → "Events" fall out structurally: ancestors see exactly one click because the re-dispatched click stops propagation at the input (`packages/react/src/checkbox/root/CheckboxRoot.tsx:247-251`), and `eventDetails.event.shiftKey` works because the synthetic dispatch carries the original event's modifier state. `preventDefault()` on the original click also stops the browser's own label/button default from generating a second, competing native click.
- **Guard layers live on the single funnel.** An input change arriving with a default-prevented native event is ignored (React #9023 workaround, `packages/react/src/checkbox/root/CheckboxRoot.tsx:212-215` — this is behavior.md → "Events" "click already preventDefault()-ed is ignored"); `readOnly` re-preventDefaults and bails there too (`packages/react/src/checkbox/root/CheckboxRoot.tsx:217-220`), so direct input clicks are covered, not just root clicks.
- **Enter is deliberately not a toggle.** `onKeyDown` intercepts Enter (`packages/react/src/checkbox/root/CheckboxRoot.tsx:322-364`), calls `event.preventBaseUIHandler()` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:329`) to mute the shared button layer's Enter handling, and bails if the event is already default-prevented (`packages/react/src/checkbox/root/CheckboxRoot.tsx:331-333`). It then swaps `preventDefault` on both the synthetic and native events for recorder wrappers (`packages/react/src/checkbox/root/CheckboxRoot.tsx:340-349`), invokes the ORIGINAL native `preventDefault` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:354`) — cancelling native button activation while leaving React's `defaultPrevented` false during propagation — and queues a microtask on the owner window (`packages/react/src/checkbox/root/CheckboxRoot.tsx:356`) that restores the originals and clicks the form's default submitter via `getDefaultFormSubmitter` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:361`) only if nobody called `preventDefault()` during propagation. This two-phase dance is exactly what behavior.md → "Keyboard interactions" observes: ancestors see `defaultPrevented === false`, consumer/ancestor `preventDefault()` still suppresses submission, and a disabled default submitter is targeted (and no-ops) rather than skipped.
- **Two id lanes.** `rootId = nativeButton ? controlId : id` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:108`): in the default mode the labelable control id lives on the hidden input and the visible element carries the internal instance id; in `nativeButton` mode the visible element IS the labelable control, so it takes `controlId` and the input takes none. This single line explains behavior.md → "Accessibility" label-`for` targets and "the hidden input does not steal the consumer's id".

The Indicator is a pure leaf: a `span` rendered from the root's state plus its own `transitionStatus`, with no DOM structure of its own beyond what the consumer's `render`/children provide (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:59-68`).

## Anything in source not explained by any test

Flagged explicitly for the golden-fixture stage and the backward-looking audit; none of these are silently dropped:

1. **Field-control re-registration on toggle.** `useRegisterFieldControl` receives the live `checked` value (`packages/react/src/checkbox/root/CheckboxRoot.tsx:152`), so registration-side effects keyed on checkedness are invisible to this unit's tests — the nearest assertion lives in `packages/react/src/form/Form.test.tsx`, outside the mined unit (behavior.md has no corresponding section).
2. **Parent-checkbox disabled bookkeeping.** Children publish `disabled` into `parentContext.disabledStatesRef` keyed by `value` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:265-276`). What the parent does with that map lives in `checkbox-group`; no test in either direction is present in this unit. This is an untested seam between the two units.
3. **`value` falls back to `name`** (`packages/react/src/checkbox/root/CheckboxRoot.tsx:96`) and the React <19 conditional `value` spread that avoids rendering an empty value (`packages/react/src/checkbox/root/CheckboxRoot.tsx:256-260`): neither the fallback nor the workaround is directly asserted by this unit's tests (behavior.md's `value`/`name` tests pass explicit values and check attribute placement only).
4. **`data-parent` styling hook.** `PARENT_CHECKBOX` is exported (`packages/react/src/checkbox/root/CheckboxRoot.tsx:38`) and rendered for parent checkboxes (`packages/react/src/checkbox/root/CheckboxRoot.tsx:303`), but no test asserts it and it appears nowhere in behavior.md's attribute list.
5. **Hidden-input focus forwarding.** The input's `onFocus` → `controlRef.current?.focus()` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:252-254`) is never directly asserted; behavior.md's focus tests drive Tab on the visible control, and its label tests assert toggling, not where focus lands.
6. **Parents skip validation-input registration** (`parent ? undefined : registerInput`, `packages/react/src/checkbox/root/CheckboxRoot.tsx:164`): plausible-but-unasserted; no test covers a parent checkbox under Field validation.
7. **The two hidden-input style modes.** `name ? visuallyHiddenInput : visuallyHidden` (`packages/react/src/checkbox/root/CheckboxRoot.tsx:207`) switches styling based on form participation, but every test only observes that the input is hidden; no test distinguishes the two modes.

Explained-but-worth-noting (not gaps): the `batch: true` flag on `useOpenChangeComplete` (`packages/react/src/checkbox/indicator/CheckboxIndicator.tsx:39`) is the mechanism behind behavior.md → "Edge cases" batched single-commit removal; the indeterminate short-circuit in the `checked` mapping (`packages/react/src/checkbox/utils/getCheckboxStateAttributesMapping.ts:10-14`) is why `data-checked`/`data-unchecked` are mutually exclusive and both absent while `data-indeterminate` shows (behavior.md → "State model").
