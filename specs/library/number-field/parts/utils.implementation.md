# NumberField — private utils (`utils` batch) — implementation mining

Ground truth for WHAT: `specs/library/number-field/parts/utils.md` (behavior sections cited by name below). This batch covers `packages/react/src/number-field/utils/` — `constants.ts`, `getViewportRect.ts` (+test), `parse.ts` (+test), `stateAttributesMapping.ts`, `types.ts`, `validate.ts` (+test). All are module-scope pure functions/constants/types; nothing in this batch defines a component, hook, context, or portal. No `TODO.md` entry exists for this unit, so there is no `wraps-external:` delegation to report.

## State machine / hooks used

**No hooks and no reactive state exist in this batch.** The "state machine" here is the ordered pure-data pipeline inside each function; React lifecycle involvement is zero.

- **`parse.ts` — a normalize-reduce pipeline.** `parseNumber` is structured as: (1) strip Unicode format/bidi controls (`\p{Cf}`) and trim (`packages/react/src/number-field/utils/parse.ts:113`), (2) canonicalize every minus/plus glyph variant to ASCII (`packages/react/src/number-field/utils/parse.ts:116`, tables at `packages/react/src/number-field/utils/parse.ts:61-64`), (3) strip a leading *or trailing* sign while recording negativity via the `takeSign` closure (`packages/react/src/number-field/utils/parse.ts:118-128`), (4) detect the locale heuristically when none was given — Arabic/Persian digits ⇒ `ar`, Han numerals ⇒ `zh` (`packages/react/src/number-field/utils/parse.ts:130-138`) — because `getNumberLocaleDetails` needs a locale to resolve separators, (5) build a `replacements` table of `[RegExp, replacement]` pairs and `reduce` it over the string (`packages/react/src/number-field/utils/parse.ts:169-188`), (6) mixed-locale dot collapse keeping only the last `.` as decimal (`packages/react/src/number-field/utils/parse.ts:191-194`), (7) `parseFloat` (`packages/react/src/number-field/utils/parse.ts:203`), (8) post-parse percent/permille rescaling via exponent shifting (`packages/react/src/number-field/utils/parse.ts:205-214`). WHY a replacements *table*: each locale feature (group, decimal, currency, unit, percent, permille, exponent, numeral system) contributes one independent regex, so supporting a new locale quirk is additive; the reduce keeps application order explicit (group removal must precede decimal canonicalization, symbol stripping must precede numeral conversion, etc.).
  - The replacement table's regexes are derived from `Intl` itself, not hardcoded: unit labels come from `formatToParts(1)` filtered to `unit` parts, escaped and joined (`packages/react/src/number-field/utils/parse.ts:146-150`); currency from the locale details (`packages/react/src/number-field/utils/parse.ts:176`); exponent separator → `e` (`packages/react/src/number-field/utils/parse.ts:180`).
  - `shiftDecimal` (`packages/react/src/number-field/utils/parse.ts:56-59`) scales by manipulating the decimal exponent string (`coefficient + 'e' + (exponent + delta)`) instead of multiplying by `0.01`/`0.001`, avoiding a second rounding error before the `Number.isFinite` guard (`packages/react/src/number-field/utils/parse.ts:216-218`). This is what makes the percent/permille/scientific cases in behavior section "parseNumber — accepted formats" hold (e.g. `1e-7%` → `1e-9`).
  - Numeral-system decoding is arithmetic, not per-character tables: Arabic-Indic/Persian/fullwidth ranges all start at code points divisible by 16, so `charCode % 16` yields the digit (`packages/react/src/number-field/utils/parse.ts:10`, `packages/react/src/number-field/utils/parse.ts:182`); Han numerals use a digit-ordered string with *both* zero glyphs first so `max(indexOf - 1, 0)` maps each glyph (`packages/react/src/number-field/utils/parse.ts:5`, `packages/react/src/number-field/utils/parse.ts:183`). The full-range round-trips proving these are in behavior section "parseNumber — accepted formats" (numeral systems bullet).
  - Regex hygiene is deliberate: every regex used with `.test()` per character is non-global to avoid `lastIndex` state leaking between calls (`packages/react/src/number-field/utils/parse.ts:25-28`, `packages/react/src/number-field/utils/parse.ts:46-50`); only the `.replace` passes use `/g` variants. `isNumeralChar` is a one-character membership predicate over the union numeral regex (`packages/react/src/number-field/utils/parse.ts:30-35`) — behavior section "isNumeralChar".
- **`validate.ts` — the validation pipeline is an ordered machine whose step order is the specification.** `toValidatedNumber` runs: null passthrough → directional snap → clamp → precision-preservation early exit → format rounding → final clamp (`packages/react/src/number-field/utils/validate.ts:103-135`). Each ordering constraint is pinned by a test and documented as behavior (behavior section "State model (controlled/uncontrolled, defaults, transitions)" items 1–5). WHY each order:
  - *Snap before clamp*: snapping is floor/ceil toward the movement direction (`packages/react/src/number-field/utils/validate.ts:87-89`), so letting the clamp run last keeps non-step-aligned min/max reachable (behavior section "State model" item 4).
  - *Clamp before round*: a below-min value with an integer format must be pulled into range first so the rounded result matches the displayed text (behavior section "State model" item 3; both passes exist because rounding can nudge the value back out — `packages/react/src/number-field/utils/validate.ts:118-123`, `packages/react/src/number-field/utils/validate.ts:134-135`).
  - *Round after snap*: `roundingMode` must act on the post-step value (behavior section "State model" item 1).
  - *Early exit before rounding*: parsed input and controlled values that involve no step arithmetic and no format rounding options are returned verbatim so >15-significant-digit input survives (`packages/react/src/number-field/utils/validate.ts:130-132`) — behavior section "toValidatedNumber — precision preservation".
  - Directional snapping uses a signed tolerance (`stepSize * STEP_EPSILON_FACTOR * sign(step)`, `packages/react/src/number-field/utils/validate.ts:6`, `packages/react/src/number-field/utils/validate.ts:80`) added to the step count *before* floor/ceil, which is what prevents fractional-step increments from re-snapping to the previous value (behavior section "toValidatedNumber — snapping to step", fractional-step cases). The `small` (alt-key) mode switches to nearest-rounding on the signed step count (`packages/react/src/number-field/utils/validate.ts:84`), and the snap base swaps to `minWithZeroDefault` for small steps or when min is unbounded (`packages/react/src/number-field/utils/validate.ts:111`) so alt-steps snap against zero-origin rather than `MIN_SAFE_INTEGER`.
  - `removeFloatingPointErrors` is a two-mode machine: (a) no rounding options → `toPrecision(15)` cleanup, *delta-bounded* by `min(EPSILON·max(1,|value|), MAX_FLOATING_POINT_CLEANUP_DELTA)` so large-magnitude real precision is never corrupted (`packages/react/src/number-field/utils/validate.ts:44-56`; the two constants are independent despite equal values, per the comment at `packages/react/src/number-field/utils/validate.ts:7-9`); (b) rounding options present → round-trip through an `en-US` formatter with display-only decoration neutralized (`signDisplay`, `currencySign`, compact→standard, `useGrouping: false` — `packages/react/src/number-field/utils/validate.ts:59-66`), parse back via this unit's `parseNumber` (`packages/react/src/number-field/utils/validate.ts:68`), and only accept the rounded value if re-formatting it reproduces the same text (`packages/react/src/number-field/utils/validate.ts:74`). That invertibility check is the guard behind the non-invertible cases in behavior section "removeFloatingPointErrors" (scientific zero buckets, `signDisplay: 'never'`, directional percent boundaries, percent overflow): if the format destroys information, the original value wins. Percent style rounds "at display scale" for free because `Intl` formats ×100 and `parseNumber` ÷100s back — no manual scaling code exists.
  - The local `NumberFormatOptionsWithRounding` type shim exists only because the repo compiles against es2022 Intl lib types (`packages/react/src/number-field/utils/validate.ts:11-17`); `hasNumberFormatRoundingOptions` doubles as that shim's type guard (`packages/react/src/number-field/utils/validate.ts:19-31`).
- **`constants.ts` — parameters of an external state machine.** `START_AUTO_CHANGE_DELAY = 400` and `CHANGE_VALUE_TICK_DELAY = 60` (`packages/react/src/number-field/utils/constants.ts:1-2`) are the press-and-hold repeat timings of the stepper. The machine itself lives outside this unit in `packages/react/src/internals/usePressAndHold.ts` (cited, not derived), wired by the stepper batch: initial tick fires immediately on press, then `startDelay` starts the repeating `tickInterval` (`packages/react/src/internals/usePressAndHold.ts:155-156`), invoked from `useNumberFieldStepperButton`'s `tick` callback which computes the step amount from modifier keys and calls the root's `incrementValue` (`packages/react/src/number-field/root/useNumberFieldStepperButton.ts:101-118`). See "Anything in source not explained by any test" for the duplicate-constants caveat.
- **`getViewportRect.ts` — a three-branch resolution machine** for the region the scrub cursor wraps within (comment at `packages/react/src/number-field/utils/getViewportRect.ts:3`): explicit `teleportDistance` → scrub-area rect padded by half the distance per side (`packages/react/src/number-field/utils/getViewportRect.ts:7-15`; the half-distance is why the cursor "teleports" to the opposite edge after crossing half the padded zone); else `visualViewport` bounds via `offsetLeft/offsetTop + width/height` (`packages/react/src/number-field/utils/getViewportRect.ts:17-26`); else document element client dimensions (`packages/react/src/number-field/utils/getViewportRect.ts:28-33`). Behavior: sections "DOM structure & portal behavior" and "Edge cases → getViewportRect — environment fallbacks" of `specs/library/number-field/parts/utils.md`.
- **`stateAttributesMapping.ts` / `types.ts` — declarative only.** The mapping is a plain object (`packages/react/src/number-field/utils/stateAttributesMapping.ts:5-9`) and `types.ts` is type-only; neither participates in any state machine.

## Context providers/consumers

**This batch defines no context and consumes no context.** Two batch members are, however, the plumbing between the root's context and the rendered parts:

- `types.ts` is the contract layer of `NumberFieldRootContext`: `NumberFieldRootContext.getStepAmount`/`incrementValue` are typed with `EventWithOptionalKeyState` and `IncrementValueParameters` from this batch (`packages/react/src/number-field/root/NumberFieldRootContext.ts:4`, `packages/react/src/number-field/root/NumberFieldRootContext.ts:13-14`). `EventWithOptionalKeyState` deliberately duck-types only `altKey`/`shiftKey` (`packages/react/src/number-field/utils/types.ts:23-26`) so stepper/keyboard/wheel/scrub code can read modifier state without a full `SyntheticEvent` — that's how `getStepAmount` picks small vs large step amounts in the root (`packages/react/src/number-field/root/NumberFieldRoot.tsx:203`) and in the stepper `tick` (`packages/react/src/number-field/root/useNumberFieldStepperButton.ts:105`). `DirectionalChangeReason` restricts change reasons to the five directional ones by picking `REASONS` constants (`packages/react/src/number-field/utils/types.ts:5-10`) from `packages/react/src/internals/reason-parts.ts:14-15` and `packages/react/src/internals/reason-parts.ts:31-32` (re-exported through `packages/react/src/internals/reasons.ts:1-4`); `ChangeEventCustomProperties.direction` (`packages/react/src/number-field/utils/types.ts:12-14`) is the payload the root attaches to change events.
- `stateAttributesMapping` is the state→`data-*` mapping each part forwards to `useRenderElement` (outside this unit): it suppresses `inputValue` and `value` from becoming DOM attributes (they would churn on every keystroke and leak values into markup) and delegates validity rendering to the shared `fieldValidityMapping` (`packages/react/src/number-field/utils/stateAttributesMapping.ts:5-9` → `packages/react/src/internals/field-constants/constants.ts:34-43`), which emits no attribute for `valid: null`, `data-valid` for `true`, `data-invalid` for `false`. Consumers that pass it through: root (`packages/react/src/number-field/root/NumberFieldRoot.tsx:21`, used at `packages/react/src/number-field/root/NumberFieldRoot.tsx:488`), input (`packages/react/src/number-field/input/NumberFieldInput.tsx:24`, used at `packages/react/src/number-field/input/NumberFieldInput.tsx:459`), group (`packages/react/src/number-field/group/NumberFieldGroup.tsx:6`, used at `packages/react/src/number-field/group/NumberFieldGroup.tsx:27`), stepper button (`packages/react/src/number-field/root/useNumberFieldStepperButton.ts:16`, used at `packages/react/src/number-field/root/useNumberFieldStepperButton.ts:188`), scrub area (`packages/react/src/number-field/scrub-area/NumberFieldScrubArea.tsx:13`), scrub area cursor (`packages/react/src/number-field/scrub-area-cursor/NumberFieldScrubAreaCursor.tsx:9`, used at `packages/react/src/number-field/scrub-area-cursor/NumberFieldScrubAreaCursor.tsx:55`).

## DOM/portal strategy and why

**No DOM is created and nothing is portaled by this batch** (consistent with behavior section "DOM structure & portal behavior"). The single DOM interaction is *measurement* in `getViewportRect`:

- It reads geometry from the caller-provided `scrubAreaEl` with `getBoundingClientRect()` (`packages/react/src/number-field/utils/getViewportRect.ts:8`) and returns *absolute* viewport-edge coordinates (`left/top/right/bottom`), i.e. a rectangle rather than a size — the scrub cursor logic (scrub-area batch, not this unit) needs edges to detect wrap-around, not a box origin.
- The window is resolved from the element via `ownerWindow` (`packages/react/src/number-field/utils/getViewportRect.ts:5`) instead of a global `window`, keeping the function correct for elements in other realms/iframes per the repo's owner-utility convention.
- The visual-viewport branch exists so a pinch-zoomed page yields the *visible* region rather than the layout viewport (the browser-only test mocks a zoomed viewport precisely so the two cannot coincide — behavior section "Edge cases → getViewportRect — environment fallbacks"). The document-element branch is the jsdom/legacy fallback (`packages/react/src/number-field/utils/getViewportRect.ts:28-33`).
- Everything else in the batch is DOM-free on purpose: `parseNumber`/`removeFloatingPointErrors`/`toValidatedNumber` must stay pure so the input, stepper, and scrub paths can call them from event handlers, effects, and render-time derivations alike without DOM coupling.

## Anything in source not explained by any test

- **`constants.ts` has no runtime consumer — only tests import it.** `CHANGE_VALUE_TICK_DELAY`/`START_AUTO_CHANGE_DELAY` are referenced solely by the stepper tests, which tick the fake clock at those cadences to mirror hold-to-repeat (`packages/react/src/number-field/increment/NumberFieldIncrement.test.tsx:6` with ticks at `packages/react/src/number-field/increment/NumberFieldIncrement.test.tsx:303-322`; `packages/react/src/number-field/decrement/NumberFieldDecrement.test.tsx:6` with ticks at `packages/react/src/number-field/decrement/NumberFieldDecrement.test.tsx:178-188`). The actual defaults live duplicated inside `usePressAndHold` as `DEFAULT_TICK_DELAY = 60` / `DEFAULT_START_DELAY = 400` (`packages/react/src/internals/usePressAndHold.ts:10-11`), and `useNumberFieldStepperButton` passes neither override (`packages/react/src/number-field/root/useNumberFieldStepperButton.ts:101-118`). So the timing contract is real and test-pinned, but the two constant pairs are independent sources of truth that could silently diverge; nothing in this batch's tests would catch a change to `usePressAndHold`'s defaults.
- **`stateAttributesMapping` is untested at this level.** The `inputValue`/`value` suppression and the `fieldValidityMapping` spread have no coverage in `packages/react/src/number-field/utils/` — the behavior spec's utility scope (`specs/library/number-field/parts/utils.md`, "Public API surface (props, parts, subcomponents)") lists only the six functions. Any guarantee that `data-value`-style attributes never leak, and the null/valid/invalid attribute behavior, is enforced (if at all) by the component-batch tests, not here.
- **`types.ts` has no runtime footprint** — all four exports are types (`packages/react/src/number-field/utils/types.ts:1-26`), so no test can exercise them; they are pinned only indirectly through consumer call sites (root context signatures, stepper tick).
- **Several `parse.ts` exports are consumed only outside this batch and untested here**: the symbol tables `PERCENTAGES`/`PERMILLE` (`packages/react/src/number-field/utils/parse.ts:13-14`), `BASE_NON_NUMERIC_SYMBOLS` (`packages/react/src/number-field/utils/parse.ts:37-44`), `SPACE_SEPARATOR_RE` (`packages/react/src/number-field/utils/parse.ts:45`), `PLUS_SIGNS_WITH_ASCII`/`MINUS_SIGNS_WITH_ASCII` (`packages/react/src/number-field/utils/parse.ts:51-52`), and `getFormatParts` (`packages/react/src/number-field/utils/parse.ts:75-77`) exist to build the root's allowed-character set (`packages/react/src/number-field/root/NumberFieldRoot.tsx:24-31`, `packages/react/src/number-field/root/NumberFieldRoot.tsx:147-197`); `FULLWIDTH_DECIMAL`/`FULLWIDTH_GROUP` (`packages/react/src/number-field/utils/parse.ts:17-18`) are referenced only by the inline fullwidth replacement regex at `packages/react/src/number-field/utils/parse.ts:173-174`. Their individual membership (e.g. that `﹢` counts as a plus, that Arabic `٬` is a non-numeric symbol) is behaviorally covered only insofar as `parseNumber`/`isNumeralChar` tests exercise the underlying regexes — the exported tables themselves are not directly asserted anywhere.
- **`getNumberLocaleDetails`'s decimal-separator override branch is only lightly pinned.** The re-resolution of the decimal separator from a plain `formatToParts(0.1)` pass over the options-derived parts (`packages/react/src/number-field/utils/parse.ts:90-104`) is exercised only via the integer-format-adjacent paths indirectly; no test in `packages/react/src/number-field/utils/parse.test.ts` passes format options that *omit* a decimal separator and asserts the fallback separator is still locale-correct.
