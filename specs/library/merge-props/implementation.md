# mergeProps — implementation spec

Stage 2 mining. Ground truth for WHAT is `specs/library/merge-props/behavior.md`, referred to below by section name only. Sources mined: `packages/react/src/merge-props/index.ts` and `packages/react/src/merge-props/mergeProps.ts`.

## State machine / hooks used

No hooks and no React runtime usage at all. The single import of React, `packages/react/src/merge-props/mergeProps.ts:1`, is used exclusively in type positions: `React.ElementType` `packages/react/src/merge-props/mergeProps.ts:5`, `React.ComponentPropsWithRef` `packages/react/src/merge-props/mergeProps.ts:6-8`, `React.CSSProperties` `packages/react/src/merge-props/mergeProps.ts:168-169`, `React.SyntheticEvent` `packages/react/src/merge-props/mergeProps.ts:268`, and `React.ComponentType` `packages/react/src/merge-props/mergeProps.ts:204-208`. There is no `useControlled`, `useIsoLayoutEffect`, state, or effect anywhere — consistent with behavior.md's "State model" section (N/A). The only shared state is the module-level `EMPTY_PROPS` constant `packages/react/src/merge-props/mergeProps.ts:10`.

The "machine" is a left-to-right accumulator fold over the argument list:

- Entrypoints: `mergeProps` declares four typed overloads for 2–5 arguments `packages/react/src/merge-props/mergeProps.ts:42-60` over one untyped implementation `packages/react/src/merge-props/mergeProps.ts:61-83`; `mergePropsN` loops over an array with identical semantics `packages/react/src/merge-props/mergeProps.ts:99-115`. `packages/react/src/merge-props/index.ts:1` re-exports everything from the module.
- Each fold step goes through `mergeInto` `packages/react/src/merge-props/mergeProps.ts:126-131`: a props-getter (any function argument, detected by `isPropsGetter` `packages/react/src/merge-props/mergeProps.ts:204-208`) REPLACES the whole accumulator by having its return value become the new `merged` `packages/react/src/merge-props/mergeProps.ts:128` (explaining behavior.md's "Edge cases" getter-replacement bullet); a props object is folded in by `mutablyMergeInto` `packages/react/src/merge-props/mergeProps.ts:153-188`.
- `mutablyMergeInto` iterates the external object and switches per key `packages/react/src/merge-props/mergeProps.ts:162-184`: `style` folds via `mergeObjects(accumulated, external)` `packages/react/src/merge-props/mergeProps.ts:166-172`; `className` folds via `mergeClassNames(accumulated, external)` `packages/react/src/merge-props/mergeProps.ts:173-176`; keys matching `isEventHandler` chain via `mergeEventHandlers(accumulated, external)` `packages/react/src/merge-props/mergeProps.ts:177-179`; everything else is overwritten outright `packages/react/src/merge-props/mergeProps.ts:181`.
- behavior.md's cross-cutting precedence rule (last argument wins) is emergent from fold direction plus these per-key strategies, not a precedence table: scalars overwrite because of `packages/react/src/merge-props/mergeProps.ts:181` (Object.assign semantics per the JSDoc `packages/react/src/merge-props/mergeProps.ts:14-15`); style keys are right-wins because `mergeObjects` spreads `{ ...a, ...b }` `packages/utils/src/mergeObjects.ts:11-13`; className is right-first because `mergeClassNames` concatenates `their + ' ' + our` `packages/react/src/merge-props/mergeProps.ts:280-287`; handlers run right-first because `mergeEventHandlers` invokes `theirHandler` before `ourHandler` `packages/react/src/merge-props/mergeProps.ts:229-249`.

Handler chaining is nested closures, not a flat handler list: `mergeProps(A, B, C)` first builds `h1 = mergeEventHandlers(A, B)` and then `h2 = mergeEventHandlers(h1, C)`. Within every pair, `their` (the later argument) runs first `packages/react/src/merge-props/mergeProps.ts:237` and the accumulated `our` side runs after unless the event is flagged `packages/react/src/merge-props/mergeProps.ts:239-241`. Recursion through the accumulator is what produces behavior.md's "Events" ordering (last-argument-first) and mid-chain vetoes: a handler calling `preventBaseUIHandler()` sets the flag on the event object, and every enclosing gate level checks the same flag after its `their` side completes.

Prevention mechanics: `makeEventPreventable` `packages/react/src/merge-props/mergeProps.ts:268-274` merely stamps `preventBaseUIHandler` (a closure that sets `baseUIHandlerPrevented = true` on the event itself, `packages/react/src/merge-props/mergeProps.ts:269-271`). It is called at every chain nesting level `packages/react/src/merge-props/mergeProps.ts:235` and for lone handlers through `wrapEventHandler` `packages/react/src/merge-props/mergeProps.ts:260-262`. There is no registry of vetoable handlers; the veto is only the flag check between the two sides of a pair `packages/react/src/merge-props/mergeProps.ts:239-241`. A handler captured by a getter and invoked manually is therefore outside any gate — this is the mechanism behind behavior.md's "Edge cases" getter-wrapping bullets, and it is documented in the JSDoc: getter-returned handlers are not automatically prevented and must self-check `baseUIHandlerPrevented` `packages/react/src/merge-props/mergeProps.ts:30-31`. Structurally, getter-returned handlers are never wrapped because wrapping only happens on two paths — `copyInitialProps` for the first (plain-object) argument `packages/react/src/merge-props/mergeProps.ts:133-148`, and `wrapEventHandler` when a later argument contributes the only handler of a key `packages/react/src/merge-props/mergeProps.ts:225-227` — and a getter bypasses both by replacing the accumulator. The leading-getter path defensively spreads the getter result (`{ ...resolvePropsGetter(...) }`, `packages/react/src/merge-props/mergeProps.ts:117-124`) so later merging mutates the copy, not the getter's object — the mechanism behind behavior.md's "returns a fresh merged props object" and "getter's returned object is never mutated" claims.

Classification: `isEventHandler` `packages/react/src/merge-props/mergeProps.ts:190-202` is purely lexical — key starts with `on`, third character is uppercase, value is a function or `undefined` `packages/react/src/merge-props/mergeProps.ts:200`. It treats `onClick`, `onContextMenu`, `onValueChange`, and `onOpenChange` identically. The synthetic-vs-nonstandard split that behavior.md's "Events" section flags UNVERIFIED is decided at invocation time, not by key: `isSyntheticEvent` duck-types on the presence of `nativeEvent` `packages/react/src/merge-props/mergeProps.ts:292-294` and branches the chain between the flag-gated path `packages/react/src/merge-props/mergeProps.ts:232-244` and the unconditional run-both path `packages/react/src/merge-props/mergeProps.ts:246-248`. So prevention capability follows the shape of the first invocation argument, regardless of the handler's key.

`ref` is intentionally unmerged (JSDoc warning `packages/react/src/merge-props/mergeProps.ts:33`); the implementation does nothing special for it, so it falls through the scalar-overwrite path.

## Context providers/consumers

No React context is created or consumed. The boundary this unit mediates is internal-props vs external/user-props: the JSDoc of `mutablyMergeInto` frames the later object as "external props take precedence" `packages/react/src/merge-props/mergeProps.ts:150-151`. The primary consumer is the central render pipeline `internals/useRenderElement`, which imports all three exports `packages/react/src/internals/useRenderElement.tsx:11` and uses `mergeClassNames` to fold state-driven className `packages/react/src/internals/useRenderElement.tsx:110-116`, normalizes render-function props with `mergePropsN`/`mergeProps` `packages/react/src/internals/useRenderElement.tsx:121-129`, and merges `render.props` onto internal props when cloning the render element `packages/react/src/internals/useRenderElement.tsx:172`. `internals/use-button` additionally imports `makeEventPreventable` so its own composed handlers can opt into the prevention protocol `packages/react/src/internals/use-button/useButton.ts:8`, calling it before delegating to external handlers `packages/react/src/internals/use-button/useButton.ts:121-125`.

## Anything in source not explained by any test

All flagged gaps, cited to source; none are covered by the unit's suite (behavior.md's "Public API surface" and "Events" sections already mark the adjacent single-argument and classification points UNVERIFIED):

1. Falsy-first-argument fast path: `packages/react/src/merge-props/mergeProps.ts:62-64` returns `createInitialMergedProps(b)` when `a`, `c`, `d`, `e` are all falsy — i.e. `mergeProps(undefined, b)` short-circuits the normal fold. Distinct from, and untested alongside, the already-UNVERIFIED single-argument call (which the normal path handles, still wrapping handlers via `copyInitialProps`).
2. Fixed arity cap: the implementation has no rest parameter `packages/react/src/merge-props/mergeProps.ts:61`; a 6th+ argument is silently dropped at runtime (the overloads `packages/react/src/merge-props/mergeProps.ts:42-60` only prevent this statically).
3. Non-leading getters are not defensively copied: `mergeInto` returns a getter's result verbatim as the new accumulator `packages/react/src/merge-props/mergeProps.ts:128`, so for `mergeProps(obj, getter, obj3)` the third argument mutates the getter-returned object through `mutablyMergeInto` `packages/react/src/merge-props/mergeProps.ts:153-188`. Only the leading-getter path copies (`packages/react/src/merge-props/mergeProps.ts:120`). behavior.md's "Edge cases" no-mutation claim is proven only for a getter in first position.
4. Shared `EMPTY_PROPS` identity: `mergePropsN([])` returns the module-level constant itself `packages/react/src/merge-props/mergeProps.ts:100-102`, and the same constant is handed to a leading getter as previous props `packages/react/src/merge-props/mergeProps.ts:120`, `packages/react/src/merge-props/mergeProps.ts:218`. A caller mutating the returned empty object would corrupt module state — untested.
5. Dead defensive branch: `resolvePropsGetter`'s `inputProps ?? EMPTY_PROPS` fallback `packages/react/src/merge-props/mergeProps.ts:218` is unreachable from both call sites (`packages/react/src/merge-props/mergeProps.ts:120`, `packages/react/src/merge-props/mergeProps.ts:128`), which are gated by `isPropsGetter`.
6. `style` reference aliasing: when exactly one side defines `style`, `mergeObjects` returns that side's object by reference `packages/utils/src/mergeObjects.ts:5-10`, so the merged `style` can alias a caller's object (same mutation hazard as #4). behavior.md's "Edge cases" only covers the both-`undefined` outcome.
7. Function-valued `className`/`style`: component prop types permit callback className/style `packages/react/src/internals/types.ts:48`, `packages/react/src/internals/types.ts:60`, but this unit never resolves them — `mergeClassNames` would string-concatenate a function `packages/react/src/merge-props/mergeProps.ts:280-287` and `style` would be shallow-spread as a plain object. Whether callbacks can reach this unit depends on callers; no test exercises it.
8. `for...in` over the external object `packages/react/src/merge-props/mergeProps.ts:162` merges inherited enumerable properties too, unlike the own-copy iteration in `packages/react/src/merge-props/mergeProps.ts:138-140`. Untested.
9. Return-value contract: a merged chain returns the rightmost handler's return value and discards the others' (`packages/react/src/merge-props/mergeProps.ts:243`, `packages/react/src/merge-props/mergeProps.ts:246-248`); behavior.md asserts nothing about handler return values.
10. Persistent event mutation: `makeEventPreventable` writes `preventBaseUIHandler` (and the flag) onto the caller's event object `packages/react/src/merge-props/mergeProps.ts:269-271`, re-stamping it at every chain level `packages/react/src/merge-props/mergeProps.ts:235`. The augmentation outlives dispatch and is observable outside the merge; behavior.md only asserts reading the flag inside handlers.
11. Public surface without unit coverage: `makeEventPreventable` `packages/react/src/merge-props/mergeProps.ts:268` and `mergeClassNames` `packages/react/src/merge-props/mergeProps.ts:276` are re-exported publicly (see previous section) but are exercised only through other units' tests — exactly the surface the golden-fixture stage should treat as part of this unit's contract.
