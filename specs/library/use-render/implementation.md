# useRender — implementation spec

Stage 2 mining. Ground truth for WHAT is `specs/library/use-render/behavior.md`, referred to below by section name only. Sources mined: `packages/react/src/use-render/index.ts`, `packages/react/src/use-render/useRender.spec.tsx`, and `packages/react/src/use-render/useRender.ts`. The unit is a one-line delegation to the shared render engine `internals/useRenderElement`, so the WHY/HOW necessarily lives mostly there; internals files are cited where the mechanism itself lives, and the dependency section enumerates the exact edges. The third listed source, `packages/react/src/use-render/useRender.spec.tsx`, is a compile-time-only type spec (`expectType` assertions, with `eslint-disable react-hooks/rules-of-hooks` `packages/react/src/use-render/useRender.spec.tsx:1` because hooks are invoked at module scope purely to check their return types) — it contributes no runtime behavior.

## State machine / hooks used

`useRender` itself contains no hook calls and no state machine — consistent with behavior.md's "State model" section (stateless, no controlled/uncontrolled dichotomy). The whole hook is one expression: `return useRenderElement(params.defaultTagName ?? 'div', params, params)` `packages/react/src/use-render/useRender.ts:19` inside the function body `packages/react/src/use-render/useRender.ts:12-20`. Three decisions are packed into that line:

1. **Default tag resolution** — `params.defaultTagName ?? 'div'` produces the engine's `element` argument, which is why behavior.md's "State model" section observes a DIV default; the parameter is typed `keyof React.JSX.IntrinsicElements | undefined` `packages/react/src/use-render/useRender.ts:79-83`.
2. **The double-pass `params, params`** — the engine's signature is `useRenderElement(element, componentProps, params)` `packages/react/src/internals/useRenderElement.tsx:22-31`, where `componentProps` is read for `render`/`className`/`style` (`UseRenderElementComponentProps`, `packages/react/src/internals/useRenderElement.tsx:287-302`) and `params` for `state/ref/props/stateAttributesMapping/enabled` (`UseRenderElementParameters`, `packages/react/src/internals/useRenderElement.tsx:246-285`). `useRender` passes its single params object as both. Because `UseRenderParameters` (`packages/react/src/use-render/useRender.ts:42-84`) exposes no `className` or `style`, the engine's `className`/`style` reads (`packages/react/src/internals/useRenderElement.tsx:63`, destructured at `:63-71`) are always `undefined` through this unit — the mechanism behind behavior.md's "DOM structure & portal behavior" observation that the hook never injects or overwrites `className` for render functions.
3. **Render selection happens downstream** — the engine does not branch on `render` until after prop assembly: `evaluateRenderProp(element, renderProp, outProps, state)` `packages/react/src/internals/useRenderElement.tsx:45-47` checks `render` first (function → `render(props, state)` `:169`; element → `React.cloneElement(render, mergedProps)` `:196`), and only falls back to the default tag when `render` is falsy (`:198-202`). This single evaluation order is the source of both precedence rules in behavior.md's "State model" section: `render` overrides `defaultTagName` because the `element` branch is reached only when `render` is falsy, and subsequent `defaultTagName` changes stay inert because nothing re-reads `element` while `render` is set.

The only hooks in the entire pipeline are inside ref merging, in `useRenderElementProps` (`packages/react/src/internals/useRenderElement.tsx:53-119`): `useMergedRefs` (up to 2 refs, `packages/utils/src/useMergedRefs.ts:22-41`) or `useMergedRefsN` (array, `packages/utils/src/useMergedRefs.ts:48-54`), both built on a memoized fork-ref object via `useRefWithInit` (`packages/utils/src/useMergedRefs.ts:36`). Two structural guards make this hook-call safe across the unit's only state-like transition, `enabled` flipping:

- A disabled call still invokes a ref hook — `void useMergedRefs(null, null)` with the comment "Called only to keep the hook order stable when disabled" `packages/react/src/internals/useRenderElement.tsx:96-98` — so hook count is identical whether enabled or not. The SAFETY comment above it `packages/react/src/internals/useRenderElement.tsx:89-94` also notes the whole block is skipped on the server (`typeof document !== 'undefined'` gate at `:95`) because refs are client-only.
- The `enabled === false` path short-circuits twice: `renderProp` is left wrapped (see Dependencies section, lazy unwrap) `packages/react/src/internals/useRenderElement.tsx:32-36`, `outProps` becomes the frozen `EMPTY_OBJECT` `packages/react/src/internals/useRenderElement.tsx:85-87, 106-108`, and the hook returns `null` `packages/react/src/internals/useRenderElement.tsx:40-42` — matching the conditional return type `Enabled extends false ? null : ReactElement` `packages/react/src/use-render/useRender.ts:86-88`.

Why the ref merging exists at all: behavior.md's "Edge cases" multi-ref bullet. `mergeProps` deliberately does not merge `ref` (JSDoc warning `packages/react/src/merge-props/mergeProps.ts:33`), so the engine attaches it manually: array form → `outProps.ref = useMergedRefsN([outProps.ref, getReactElementRef(renderProp), ...ref])` `packages/react/src/internals/useRenderElement.tsx:100`; single form → `useMergedRefs(outProps.ref, getReactElementRef(renderProp), ref)` `packages/react/src/internals/useRenderElement.tsx:102`. The first slot (`outProps.ref`) is `undefined` for the default-tag path (nothing else sets it), and `getReactElementRef(renderProp)` extracts the render element's own ref (`packages/utils/src/getReactElementRef.ts:7-16`, version-dependent: `props.ref` on React 19+, `element.ref` before, `:15`) so a `render` element's ref survives the clone instead of being clobbered by the user's refs. The merged callback fans out to every ref on attach and detaches (or runs React 19 cleanups) on detach (`packages/utils/src/useMergedRefs.ts:95-150`) — the mechanism producing "every ref in the array is attached" in behavior.md.

The state→`data-*` conversion that behavior.md's "Public API surface" (`state`) and "Edge cases" sections document is a pure function, no hooks: `getStateAttributesProps` `packages/react/src/internals/getStateAttributesProps.ts:5-32` iterates the state record (`:12`), gives `stateAttributesMapping` entries first crack (own-property check plus `null` → omit, `:15-22`), maps `true` → `data-${key.toLowerCase()}` with empty-string value (`:24-25`), and other truthy values → the same lowercased key with `value.toString()` (`:26-28`). Falsy values fall through every branch, which is exactly behavior.md's falsy-omits-attribute bullets. The attribute-level precedence rule in behavior.md's "State model" section (props beat state) is one spread order: `outProps = mergeObjects(stateProps, resolvedProps)` `packages/react/src/internals/useRenderElement.tsx:85-87`, where `mergeObjects` is a right-wins shallow spread `{ ...a, ...b }` `packages/utils/src/mergeObjects.ts:11-13` with `stateProps` as `a` and the normalized user `props` as `b`. The `?? {}` there is defensive: `EMPTY_OBJECT` is `Object.freeze({})` `packages/utils/src/empty.ts:8`, and the engine later mutates `outProps` (ref, className, style), which would throw in strict mode — the comment at `packages/react/src/internals/useRenderElement.tsx:82-84` says exactly this. `state` itself defaults to `EMPTY_OBJECT` `packages/react/src/internals/useRenderElement.tsx:44`, so `state: undefined` iterates nothing — behavior.md's "`state: undefined` is safe" edge case.

## Context providers/consumers

No React context is created, provided, or consumed anywhere in the unit or its engine — there are no `createContext`/`useContext` calls in `packages/react/src/use-render/useRender.ts` or `packages/react/src/internals/useRenderElement.tsx`. This matches behavior.md's "Accessibility", "Focus management", and "Keyboard interactions" sections being N/A: those behaviors in real components come from context plumbing that lives in the components, not in the render engine.

The boundary this unit mediates is not context but element-as-prop composition. `useRender` is designed so its returned element can be handed to another component's `render` prop — the type spec demonstrates exactly this: `const element = useRender({ defaultTagName: 'div' }); return <Button render={element} />` `packages/react/src/use-render/useRender.spec.tsx:56-59`. When a Base UI component receives such an element, its own `useRenderElement` call takes the element-clone path: `mergeProps(props, render.props)` (component internal props as accumulator, user element's props folded in, external-wins per the JSDoc `packages/react/src/merge-props/mergeProps.ts:150-151`) at `packages/react/src/internals/useRenderElement.tsx:172`, with the merged ref re-stamped afterwards (`mergedProps.ref = props.ref` `:174`) because `mergeProps` drops `ref` (`packages/react/src/merge-props/mergeProps.ts:33`). So user props set on the `useRender` element survive, and the host component's internal props fill the gaps — the composition protocol that makes this unit the public escape hatch for custom parts.

Within one call, the only other boundary is `props` normalization: `resolveRenderFunctionProps(props)` `packages/react/src/internals/useRenderElement.tsx:80, 121-129` runs user props through `mergeProps(undefined, props)` (or `mergePropsN` for arrays), which is what gives user event handlers the `preventBaseUIHandler` veto protocol (`packages/react/src/merge-props/mergeProps.ts:177-179`, `:268-274`) should any be present — though behavior.md's "Events" section is N/A and no handler ever flows through this unit's tests.

## DOM/portal strategy and why

No portal — behavior.md's "DOM structure & portal behavior" section records portal behavior as N/A, and the engine simply returns one element to be rendered wherever the caller puts it in the tree; portaling is the responsibility of higher-level components, not the render primitive. The single-element output contract in behavior.md is structural: every branch of `evaluateRenderProp` returns exactly one `ReactElement` (`packages/react/src/internals/useRenderElement.tsx:169, 196, 200`).

Two DOM decisions live in `renderTag` `packages/react/src/internals/useRenderElement.tsx:232-240`, which the default-tag branch reaches for string tags (`:198-202`):

- `button` is rendered with an implicit `type="button"` `packages/react/src/internals/useRenderElement.tsx:233-235` — without it, a rendered `<button>` inside a form would default to `type="submit"` and submit on click; Base UI components that can render non-buttons via `render` declare the counterpart through the `nativeButton` prop types (`packages/react/src/internals/types.ts:63-81`).
- `img` is rendered with an implicit `alt=""` `packages/react/src/internals/useRenderElement.tsx:236-238` — a decorative-image default that also silences the missing-alt accessibility warning; user-supplied props overwrite it via the spread in the same JSX.
- Both special cases forward `key={props.key}` explicitly (`:234, 237`); every other tag goes through `React.createElement(Tag, props)` `:239`.

Neither default is exercised by this unit's suite (behavior.md never asserts `type` or `alt`); they are engine-level DOM policy this unit inherits wholesale.

## Anything in source not explained by any test

All flagged gaps; none are covered by the unit's suite that behavior.md mined. These are exactly what the golden-fixture stage and the backward-looking audit loop must treat as part of this unit's contract independently:

1. **The entire `enabled` feature.** `enabled?: Enabled | undefined` (`packages/react/src/use-render/useRender.ts:73-78`, "If `false`, the hook will skip most of its internal logic and return `null`"), the conditional return type (`:86-88`), and every disabled branch in the engine — early `null` return `packages/react/src/internals/useRenderElement.tsx:40-42`, suppressed className/style/state-attrs `:73-78`, frozen-`EMPTY_OBJECT` outProps `:85-87, 106-108`, and the hook-order-stability stub `:96-98`. No test in this unit's suite mentions `enabled`; only the type spec asserts its type-level effect (`packages/react/src/use-render/useRender.spec.tsx:20-32`).
2. **Lazy render-prop unwrapping** (`unwrapLazyRenderProp`, `packages/react/src/internals/useRenderElement.tsx:131-156`, called at `:32-36`): a React-Flight workaround (upstream issue 32392) that unwraps a lazy wrapper handed over from a Server Component via `React.Children.toArray` before `.props`/`.ref` are read, keeping it wrapped while disabled so a pending lazy element doesn't suspend. Entirely untested here.
3. **Dev-only diagnostics:** the uppercase-function-name heuristic `warnIfRenderPropLooksLikeComponent` (`packages/react/src/internals/useRenderElement.tsx:166-168, 208-230` — fires when `render={Component}` receives a component directly, warning about Rules-of-Hooks breakage), the `React.isValidElement` guard with the custom "invalid render prop" error (`:182-194`), and the unreachable-parameter fallback throw (`:203-205`). None exercised in this suite.
4. **`renderTag` DOM defaults:** `button` → implicit `type="button"` and `img` → implicit `alt=""` (`packages/react/src/internals/useRenderElement.tsx:233-238`) — no test in behavior.md asserts either attribute.
5. **Dead/deprecated surface:** `propGetter` is declared on `UseRenderElementParameters` marked `@deprecated` (`packages/react/src/internals/useRenderElement.tsx:261`) but is never read anywhere in the engine's runtime code — dead typing carried for compatibility, and reachable through this unit's `params` double-pass.
6. **Array/function `props` forms are unreachable via this unit's public API.** The engine accepts `props` as an array of props objects or props-getter functions (`packages/react/src/internals/useRenderElement.tsx:273-280`, handled by `resolveRenderFunctionProps` at `:124-126`), but `useRender` types `props` as a plain `Record<string, unknown>` (`packages/react/src/use-render/useRender.ts:72`), so only the single-object form can arrive; behavior.md's suite proves only that form.
7. **Event-handler merging and the `preventBaseUIHandler` protocol** are latent in the `props` path (via `mergeProps`'s handler chaining, `packages/react/src/merge-props/mergeProps.ts:177-179, 221-266`) but behavior.md's "Events" section is N/A — no test drives a handler through this hook.
8. **Wholesale key lowercasing in state conversion:** `key.toLowerCase()` (`packages/react/src/internals/getStateAttributesProps.ts:25, 27`) means a camelCase state key like `isActive` becomes `data-isactive`, not `data-is-active` — behavior.md's "Edge cases" section only shows single-lowercase-word keys, and `stateAttributesMapping` is the documented route to kebab-case (`packages/react/src/use-render/useRender.ts:60-65`). The camelCase default outcome is untested.
9. **Single-ref form:** already marked UNVERIFIED in behavior.md's "Public API surface"; the mechanism is the three-argument `useMergedRefs` path (`packages/react/src/internals/useRenderElement.tsx:101-103`, `packages/utils/src/useMergedRefs.ts:22-41`), typed as accepted at `packages/react/src/use-render/useRender.ts:54`.
10. **SSR behavior:** the `typeof document !== 'undefined'` gate skips ref merging on the server (`packages/react/src/internals/useRenderElement.tsx:92-95`, rationale in the SAFETY comment `:89-94`). No SSR test exists in this suite.
11. **React-19 ref extraction branch:** `getReactElementRef` reads `props.ref` on React 19+ and `element.ref` before (`packages/utils/src/getReactElementRef.ts:15`) — the version-conditional is untested in this unit.
12. **The `Button` composition demo is type-only:** `<Button render={element} />` in `packages/react/src/use-render/useRender.spec.tsx:56-59` is checked by the compiler and never rendered at runtime, so the cross-component interop path described under "Context providers/consumers" is unproven by any test in this unit.
