# Toast Viewport — implementation spec (ToastViewport, ToastViewportCssVars, ToastViewportDataAttributes, focusVisible)

Scope: implementation mining for the `toast` unit, batch `viewport`. Evidence is the four batch source files — `packages/react/src/toast/viewport/ToastViewport.tsx`, `packages/react/src/toast/viewport/ToastViewportCssVars.ts`, `packages/react/src/toast/viewport/ToastViewportDataAttributes.ts`, `packages/react/src/toast/utils/focusVisible.ts` — plus the outside-unit imports they pull in. This spec explains WHY/HOW behind the behavior documented in `specs/library/toast/parts/viewport.md` (below: "part spec") and `specs/library/toast/behavior.md` (below: "behavior spec"); it does not restate either. The unit's TODO entry carries no `wraps-external:` field (`TODO.md:538-547`), so nothing here is a third-party delegation — all behavior is derived from the unit's own source.

## State machine / hooks used

### No local React state — the store is the state machine

`ToastViewport` declares zero `useState`/`useReducer`. Every reactive value is read off the `ToastStore` instance obtained from context (`packages/react/src/toast/viewport/ToastViewport.tsx:28`) via `store.useState(...)`, the selector-keyed subscription API of `ReactStore` (`packages/utils/src/store/ReactStore.ts:171-179`). The reads are `'isEmpty'`, `'toasts'`, `'focused'`, `'expanded'`, `'prevFocusElement'` (`packages/react/src/toast/viewport/ToastViewport.tsx:35-39`), mapping to store selectors `isEmpty` (`packages/react/src/toast/store.ts:88`), `focused` / `expanded` / `prevFocusElement` (`packages/react/src/toast/store.ts:93-96`). The crucial asymmetry: `expanded` is a *derived* selector — `hovering || focused` (`packages/react/src/toast/store.ts:94`) — so the component never writes expansion; it writes only the two inputs (`hovering`, `focused`) plus `prevFocusElement`/`isWindowFocused`, and the `data-expanded` attribute falls out as a projection of them.

Writes go through the single-key `store.set(...)` inherited from `Store` (`packages/utils/src/store/Store.ts:106`). Per-render derived values are plain locals: `frontmostHeight = toasts[0]?.height` (`packages/react/src/toast/viewport/ToastViewport.tsx:40`) leans on the store's newest-first array order (behavior spec, "State model"), `hasTransitioningToasts` (`packages/react/src/toast/viewport/ToastViewport.tsx:42`) drives the deferred-collapse effect, and `highPriorityToasts` (`packages/react/src/toast/viewport/ToastViewport.tsx:43`) drives the a11y mirror (below).

Truly non-render state is held in refs, not state, precisely because none of it should trigger a render by itself:

- `handlingFocusGuardRef` (`packages/react/src/toast/viewport/ToastViewport.tsx:31`) — a one-shot latch suppressing the single focus event caused by focusing a guard span (see Focus-guard choreography).
- `markedReadyForMouseLeaveRef` (`packages/react/src/toast/viewport/ToastViewport.tsx:32`) — the deferred-collapse intent latch.
- `touchActiveRef` (`packages/react/src/toast/viewport/ToastViewport.tsx:33`) — "a touch gesture is in progress" latch.
- `windowFocusTimeout = useTimeout()` (`packages/react/src/toast/viewport/ToastViewport.tsx:29`; hook at `packages/utils/src/useTimeout.ts:46-52`) — a one-shot 0 ms deferral used as an event-ordering guard.

### The pause/resume protocol

The viewport owns no timers; auto-dismiss scheduling lives entirely in the store's timer map (manager batch — cited only: `packages/react/src/toast/store.ts`). The viewport's job is to flip the three "pause inputs" (`hovering`, `focused`, `isWindowFocused`) and call `store.pauseTimers()` / `store.resumeTimers()` (`packages/react/src/toast/store.ts:364-380`, `packages/react/src/toast/store.ts:382-396`) at the exact transitions the part spec documents ("State model", "Keyboard interactions", "Focus management"):

- `handleMouseEnter` (`packages/react/src/toast/viewport/ToastViewport.tsx:155-159`): `pauseTimers()` + `hovering: true` + clears the leave latch. It is bound to **both** `onMouseEnter` and `onMouseMove` (`packages/react/src/toast/viewport/ToastViewport.tsx:224-225`), so pointer movement re-asserts hover, not just entry.
- `handleFocus` (`packages/react/src/toast/viewport/ToastViewport.tsx:189-206`): three gates in order — the guard latch (`190-193`), an already-focused early return (`195-197`), then the focus-visible gate: expansion/pause happen only when the active element matches `:focus-visible` (`202-205`, via `isFocusVisible` on `activeElement(ownerDocument(...))`). This is the mechanism behind "clicking inside without keyboard navigation" not freezing timers — mouse focus is not focus-visible.
- `handleBlur` (`packages/react/src/toast/viewport/ToastViewport.tsx:208-215`): only when currently focused **and** `event.relatedTarget` is not inside the viewport (`contains` check at `packages/react/src/toast/viewport/ToastViewport.tsx:209`) does it clear `focused` and call `resumeTimersIfWindowFocused` (`packages/react/src/toast/viewport/ToastViewport.tsx:161-165`). That wrapper's `isWindowFocused` guard is exactly why "viewport blur while the window is blurred" does not resume timers (part spec, "Focus management").
- The F6 handler (`packages/react/src/toast/viewport/ToastViewport.tsx:58-66`): snapshots the current active element into `prevFocusElement` (`61`), programmatically focuses the viewport with `preventScroll` (`62`), pauses timers (`63`), and sets `focused: true` (`64`). `tabIndex: -1` in the default props (`packages/react/src/toast/viewport/ToastViewport.tsx:218`) is what makes this programmatic focus possible without adding the viewport to the tab order.

### The deferred-collapse latch (`flushMouseLeave`)

This is the most stateful piece of the batch and implements the part spec's "pointercancel ordering" and "deferred collapse during exit animation" edge cases directly:

- `handleMouseLeave` (`packages/react/src/toast/viewport/ToastViewport.tsx:167-172`) does not collapse by itself: it sets `markedReadyForMouseLeaveRef` (the *intent* to collapse) and immediately runs `flushMouseLeave`.
- `flushMouseLeave` (`packages/react/src/toast/viewport/ToastViewport.tsx:136-151`) bails out while toasts are animating out (`hasEndingToasts`, recomputed fresh from the store at `137`), while a touch gesture is active (`touchActiveRef`), or while no intent was marked. Otherwise it resumes timers only if the window is focused (`146-148` — the guard behind "mouseleave while blurred must not resume", part spec "Events"), then sets `hovering: false` (`149`) and resets the latch (`150`).
- The deferred retry is an effect keyed on the `hasTransitioningToasts` boolean: `React.useEffect(flushMouseLeave, [hasTransitioningToasts, store])` (`packages/react/src/toast/viewport/ToastViewport.tsx:153`). When the last exit animation finishes and that boolean flips, the blocked mouseleave is finally applied — producing "collapse applied only after the closing toast unmounts" (part spec, "Edge cases") without any animation-completion callback in this file.
- Touch: `handlePointerDown` latches `touchActiveRef` for `pointerType === 'touch'` (`packages/react/src/toast/viewport/ToastViewport.tsx:174-178`); `handlePointerEnd` (bound to both `onPointerUp` and `onPointerCancel`, `packages/react/src/toast/viewport/ToastViewport.tsx:232-233`) clears the latch and re-runs `flushMouseLeave` (`180-187`). The latch ordering is what makes "pointercancel without a preceding mouseleave keeps the viewport expanded" and "pointercancel after mouseleave collapses it" fall out of one code path: in the first case the leave latch was never set, in the second it was and the gesture no longer blocks it.
- Note the latches can only *block* collapse; nothing here can force expansion, which remains the pure `hovering || focused` selector.

### Global listener lifecycle (the effect)

`React.useEffect` at `packages/react/src/toast/viewport/ToastViewport.tsx:45-102` attaches exactly four listeners, gated on `store.state.viewport && !isEmpty` (`49-52`). The gate on `isEmpty` (a store-level selector, not a DOM check) is doubly deliberate:

1. The inline comment (`46-48`) records the ref-timing reason: `store.state.viewport` is `null` on the first render (the `setViewport` ref callback has not committed), and `isEmpty` re-runs the effect when the first toast lands, by which time the node exists.
2. It explains why F6 still works with `limit: 0` and no rendered toast (part spec, "Keyboard interactions"): limited toasts still exist in the store's `toasts` array, so `isEmpty` is `false` and the listeners are attached even though the viewport renders no toast children.

`ownerWindow(viewport)` / `ownerDocument(viewport)` (`packages/react/src/toast/viewport/ToastViewport.tsx:54-55`; `packages/utils/src/owner.ts:1-5`) bind the listeners to whatever realm the viewport DOM node actually lives in — this single choice produces the cross-realm iframe behavior in the part spec ("DOM structure & portal behavior") with zero extra code.

The four listeners, combined via `mergeCleanups` (`packages/utils/src/mergeCleanups.ts:6-15`) so one effect cleanup removes all of them, with each `addEventListener` call returning its own removal closure (`packages/utils/src/addEventListener.ts:52-62`):

- Window `keydown` (`packages/react/src/toast/viewport/ToastViewport.tsx:57-66`) — the F6 handler above. `getTarget(event) !== viewport` (`59`) skips a keydown that already originated on the viewport so F6 does not steal focus from itself.
- Window `blur`, capture (`packages/react/src/toast/viewport/ToastViewport.tsx:68-75`) — `getTarget(event) !== win` (`69`) filters element-level `blur` events that traverse the window during the capture phase (blur does not bubble, but capture-phase listeners on `window` still see events dispatched on descendants); only a genuine window blur sets `isWindowFocused: false` and pauses.
- Window `focus`, capture (`packages/react/src/toast/viewport/ToastViewport.tsx:77-94`) — mirrored filter: `event.relatedTarget` is set for element-level focus events and only absent for window focus (`78-80`). The resume decision (`82-90`) resumes timers in every case *except* focus returning into the viewport with keyboard focus-visible — i.e. `target === win || !contains(viewport, target) || !isFocusVisible(activeEl)`. Then `windowFocusTimeout.start(0, ...)` (`92-93`) defers `isWindowFocused: true` by one tick so React's `onFocus` (`handleFocus`) can run first; without that ordering, window-focus would resume and the subsequent `handleFocus` would immediately re-pause with a stale flag in between.
- Document `pointerdown`, capture (`packages/react/src/toast/viewport/ToastViewport.tsx:100`) — delegates wholesale to `store.handleDocumentPointerDown` (`packages/react/src/toast/store.ts:402-416`), which implements the "touch pointerdown outside the viewport collapses and resumes; on the viewport keeps expanded; mouse ignored" rules (part spec, "State model" and "Events"). The store owns the logic because the same predicate guards timer scheduling elsewhere (manager batch).

Dependencies are `[store, windowFocusTimeout, isEmpty]` (`packages/react/src/toast/viewport/ToastViewport.tsx:102`) — the exact add/remove-once-per-non-empty-cycle rebinding the part spec asserts ("Events", "Edge cases").

### Focus-guard choreography

The guard node is computed as `!isEmpty && prevFocusElement && <FocusGuard onFocus={handleFocusGuard} />` (`packages/react/src/toast/viewport/ToastViewport.tsx:245`) — guards exist **only** while there is a remembered pre-viewport element, i.e. only after F6 has been pressed. They are rendered in three places: twice inside the viewport element as `{focusGuard}{children}{focusGuard}` (`packages/react/src/toast/viewport/ToastViewport.tsx:254-260`, where the third props entry intentionally wins the children merge over user-spread children in `elementProps`), and once outside the element as a preceding sibling (`packages/react/src/toast/viewport/ToastViewport.tsx:267`).

`handleFocusGuard` (`packages/react/src/toast/viewport/ToastViewport.tsx:104-119`) implements the part spec's guard behavior ("Focus management") as a two-branch decision on `event.relatedTarget`:

- `relatedTarget === store.state.viewport` (`110`) — the tab-forward-out-of-the-focused-viewport case: find the first toast that is neither `transitionStatus: 'ending'` nor `limited` (`109-112`) and focus its ref (`114-115`). This is the "skip toasts animating out / inert because limited" rule.
- Anything else — including shift+Tab backward from the first toast onto the leading inner guard, and forward Tab past the last toast onto the trailing guards — calls `store.restoreFocusToPrevElement()` (`117`; `packages/react/src/toast/store.ts:398-400`), which focuses the saved `prevFocusElement`. The inner-before guard thus bounces backward tabs to the pre-F6 element, and the trailing guards close the forward tab cycle.

The guard focus event itself is suppressed from expanding the viewport: setting `handlingFocusGuardRef` at `packages/react/src/toast/viewport/ToastViewport.tsx:105` makes the bubbling focus reach `handleFocus`, which consumes the latch and returns (`190-193`) instead of expanding/pausing.

`handleKeyDown` (`packages/react/src/toast/viewport/ToastViewport.tsx:121-134`) covers shift+Tab issued **on the viewport itself**: `preventDefault` (`127`) plus `restoreFocusToPrevElement` (`132`). The comment at `128-131` records the non-obvious decision: resuming timers is *not* done here — the restore blurs the viewport and `handleBlur` resumes from there; resuming in both places would also fire when the restored element lives inside the viewport (the part spec's "timers stay paused when the pre-F6 element was a toast close button" case).

## Context providers/consumers

- Exactly one context: `ToastContext`, whose value **is** the `ToastStore` instance — there is no separate context object wrapping it (`packages/react/src/toast/provider/ToastProviderContext.ts:5-7`). `useToastProviderContext()` (`packages/react/src/toast/viewport/ToastViewport.tsx:28`) unwraps it and throws the descriptive `Base UI: useToastManager must be used within <Toast.Provider>.` when absent (`packages/react/src/toast/provider/ToastProviderContext.ts:9-14`) — the context-missing rejection the part spec records ("Public API surface").
- The viewport consumes **no** per-toast context. `Toast.Root` and the leaf parts are opaque `children` to it (`packages/react/src/toast/viewport/ToastViewport.tsx:254-260`); all viewport↔root coordination (expansion, focus reorientation on close, limited flags) flows through the store's shared state rather than a React context — the store is the single coordination bus shared with the Provider batch (which syncs `timeout`/`limit` via `syncProviderProps`, cited only: `packages/react/src/toast/store.ts:119-138`) and the manager batch.

## DOM/portal strategy and why

- The viewport renders a plain `div` through `useRenderElement('div', ...)` (`packages/react/src/toast/viewport/ToastViewport.tsx:247`) and creates **no portal of its own**. Placement is the application's decision (via the `Toast.Portal` batch or a manual `createPortal`), and the component adapts to wherever it lands by deriving `window`/`document` from its own node (`54-55`) — this is why the iframe-portaled viewport binds listeners in the iframe realm with no special-case code (part spec, "DOM structure & portal behavior").
- The ref is load-bearing twice over: `ref: [forwardedRef, store.setViewport]` (`packages/react/src/toast/viewport/ToastViewport.tsx:248`) merges the user's forwarded ref with the store's `setViewport` ref callback (`packages/react/src/toast/store.ts:115-117`), so the store holds the live DOM node that store-side logic (`handleDocumentPointerDown`, `handleFocusManagement` in the manager batch) can `contains()`-test against. The ref-commit ordering is also why the listener effect keys on `isEmpty` rather than running unconditionally (above).
- The component's return value is a `Fragment`, not the element (`packages/react/src/toast/viewport/ToastViewport.tsx:265-280`): outer guard → element → high-priority alert mirror. The alert mirror is a deliberate **sibling** of the viewport, not a child, so it is not affected by viewport-level pointer/focus handling and stays live whenever `!focused && highPriorityToasts.length > 0` (`269`).
- Default attribute surface (`packages/react/src/toast/viewport/ToastViewport.tsx:217-239`): `tabIndex: -1`; `role: 'region'`, `aria-live: 'polite'`, `aria-atomic: false`, `aria-relevant: 'additions text'`, `aria-label: 'Notifications'` (landmark semantics UNVERIFIED by tests — part spec, "Accessibility"); the mouse/pointer/focus/key handlers; and the inline style writing the frontmost-height CSS var: `` [ToastViewportCssVars.frontmostHeight]: frontmostHeight ? `${frontmostHeight}px` : undefined `` (`234-238`). The constant is the public token `--toast-frontmost-height` (`packages/react/src/toast/viewport/ToastViewportCssVars.ts:5`); the `undefined` branch omits the var entirely when there is no frontmost toast.
- `data-expanded` is produced generically: the state object `{ expanded }` (`packages/react/src/toast/viewport/ToastViewport.tsx:241-243`) is passed to `useRenderElement`, whose `getStateAttributesProps` maps `true` → `data-expanded=""` and omits the attribute for `false` (`packages/react/src/internals/getStateAttributesProps.ts:24-28`). The component never imports the attributes module — `packages/react/src/toast/viewport/ToastViewportDataAttributes.ts:5` (`data-expanded`) is the public token for CSS targeting, kept in sync with the state key purely by the lowercased `data-${key}` naming convention.
- The props pipeline `defaultProps → elementProps → {children}` (`packages/react/src/toast/viewport/ToastViewport.tsx:250-262`) is merged by `useRenderElement` (`packages/react/src/internals/useRenderElement.tsx:22-48`), which also resolves the `render`/`className`/`style` APIs and state attributes — the conformance-proven surface ("Public API surface" in the part spec). Users can override the handlers/CSS var by spreading their own props in `elementProps`, but not the guard-wrapped children, since the third entry always wins.

## Anything in source not explained by any test

- The viewport's landmark semantics: `role: 'region'`, `aria-live: 'polite'`, `aria-atomic: false`, `aria-relevant: 'additions text'`, `aria-label: 'Notifications'` (`packages/react/src/toast/viewport/ToastViewport.tsx:219-223`). The part spec explicitly marks viewport role/aria UNVERIFIED (part spec, "Accessibility"); no test asserts any of these attributes, including the React-rendered `aria-atomic="false"` string vs the mirrored alerts' true `aria-atomic`.
- The high-priority visually-hidden alert mirror (`packages/react/src/toast/viewport/ToastViewport.tsx:269-278`): when the viewport is **not** focused and high-priority toasts exist, a sibling `div` styled with `visuallyHidden` renders one `role="alert" aria-atomic` wrapper per high-priority toast containing its `title`/`description`. No viewport test asserts this region, its per-toast structure, or its `!focused` gating (which suppresses duplicate announcement while the user is actively reading the expanded stack). The `role="alert"` element covered elsewhere (behavior spec, "Accessibility") is the one rendered by `Toast.Root`, a different node.
- `onClick: handleFocus` (`packages/react/src/toast/viewport/ToastViewport.tsx:230`): mouse clicks into the viewport run the same focus-visible gate as focus events; no test clicks the viewport to pin down that timers keep running (mouse focus is not focus-visible) or that the gate even fires.
- `onMouseMove` bound to `handleMouseEnter` (`packages/react/src/toast/viewport/ToastViewport.tsx:225`): pointer movement re-asserts hover; the tests only fire discrete `mouseenter`/`mouseleave`.
- `event.preventDefault()` in the F6 handler (`packages/react/src/toast/viewport/ToastViewport.tsx:60`): suppresses the browser's native F6 (focus-pane cycling); the part spec notes preventDefault semantics are unasserted anywhere (part spec, "Edge cases").
- The `getTarget(event) !== viewport` self-guard on F6 (`packages/react/src/toast/viewport/ToastViewport.tsx:59`): no test presses F6 while the viewport itself already has focus to assert the no-op.
- The CSS-var omission branch: the inline `--toast-frontmost-height` is `undefined` (attribute omitted) when `toasts[0]?.height` is falsy (`packages/react/src/toast/viewport/ToastViewport.tsx:234-238`). The browser-only test asserts the var is non-empty after a toast is added (part spec, "DOM structure & portal behavior"); nothing covers its removal when the store empties.
- The public type namespace `ToastViewport.State` / `ToastViewport.Props` / `ToastViewportState.expanded` (`packages/react/src/toast/viewport/ToastViewport.tsx:283-295`): consumed only by type-level tests (behavior spec's public-types file, `test/public-types/toast.tsx`) and the docs API; no runtime test references the state shape beyond `data-expanded`.
- `ToastViewportDataAttributes.ts` and `ToastViewportCssVars.ts` are pure constant modules (`packages/react/src/toast/viewport/ToastViewportDataAttributes.ts:1-5`, `packages/react/src/toast/viewport/ToastViewportCssVars.ts:1-5`) — no behavior to test; their only contract with the source is the naming convention that `state.expanded` (via `getStateAttributesProps`) and the inline style key produce exactly the string constants these files export.
