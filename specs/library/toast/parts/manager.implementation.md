# Toast manager — implementation spec (createToastManager, useToastManager, ToastStore, resolvePromiseOptions)

Scope: implementation mining for the `toast` unit, batch `manager`. Evidence is the seven batch source files — `packages/react/src/toast/createToastManager.ts`, `packages/react/src/toast/createToastManager.spec.tsx`, `packages/react/src/toast/useToastManager.ts`, `packages/react/src/toast/useToastManager.spec.tsx`, `packages/react/src/toast/store.ts`, `packages/react/src/toast/store.test.ts`, `packages/react/src/toast/utils/resolvePromiseOptions.ts` — plus the outside-batch imports they pull in. This spec explains WHY/HOW behind the behavior documented in `specs/library/toast/parts/manager.md` (below: "part spec") and `specs/library/toast/behavior.md` (below: "behavior spec"); it does not restate either. The unit's TODO entry carries no `wraps-external:` field (`TODO.md:534-543`), so nothing here is a third-party delegation — all behavior is derived from the unit's own source.

## State machine / hooks used

### Two frontends over one store — and only one of them is React

The batch has two deliberately different entry points into the same state:

- `createToastManager` (`packages/react/src/toast/createToastManager.ts:12-84`) is a **framework-agnostic command bus, not a state holder**. It keeps only a `Set` of listeners (`packages/react/src/toast/createToastManager.ts:13`) and translates each imperative call (`add`/`close`/`update`/`promise`) into a `ToastManagerEvent` `{ action, options }` broadcast synchronously via `emit` (`packages/react/src/toast/createToastManager.ts:15-17`). It stores no toasts, no timers, no ids. The subscriber that turns events into state changes is the Provider (shell batch, cited only); the emitted event shape is the contract between the two batches. This split is what makes the external-manager mode (part spec, "State model") work: the manager can live in a module scope outside React while the store lives inside `Toast.Provider`.
- The `' subscribe'` member (`packages/react/src/toast/createToastManager.ts:22-27`) is a **soft-private API**: the quoted, non-identifier key keeps it out of ordinary property access and autocomplete (the inline comment cites the TS-team tweet proposing the trick, `packages/react/src/toast/createToastManager.ts:20-21`), reserving it for the Provider while the public surface remains the four methods (`packages/react/src/toast/createToastManager.ts:86-99`).
- `ToastStore` (`packages/react/src/toast/store.ts:99-113`) is the **single source of truth**: `ReactStore<State, {}, typeof selectors>` with the selectors object bound at construction (`packages/react/src/toast/store.ts:104-112`). The manager methods on the store (`addToast`, `closeToast`, `updateToast`, `promiseToast`) are instance arrow-function properties so their identity is stable for the `useMemo` in the hook and for direct use in effects.

### Per-toast transition machine, enforced at one funnel

Every mutation flows through `updateToastInternal` (`packages/react/src/toast/store.ts:227-286`) or the private `setToasts` funnel (`packages/react/src/toast/store.ts:466-478`), which is what keeps the documented transitions (part spec, "State model") consistent:

- `'starting'` is stamped at add time (`packages/react/src/toast/store.ts:187`); `'ending'` is stamped by `closeToast` together with `height: 0` (`packages/react/src/toast/store.ts:305-309`) — zeroing the height immediately collapses the stack-offset accumulation in `createToastMetadata` (`packages/react/src/toast/store.ts:46-68`) while the toast is still mounted for its exit animation.
- `'ending'` is **terminal and write-protected**: `updateToastInternal` early-returns for ending toasts (`packages/react/src/toast/store.ts:242-244`), which is the mechanism behind "height writes with `transitionStatus: undefined` are ignored while transitioning out" (`packages/react/src/toast/store.test.ts:67-84`) and "a dismissed promise toast stays dismissed after resolution" (part spec, "Edge cases") — async updates simply cannot resurrect an ending toast. `updateToast` additionally refuses to *invoke the user updater* for a missing or ending id (`packages/react/src/toast/store.ts:211-215`; `packages/react/src/toast/store.test.ts:145-155`), so user code with side effects doesn't run for updates the store would discard.
- `updateKey` is a monotonic change counter: stamped `0` at add (`packages/react/src/toast/store.ts:186`; the test factory mirrors this invariant at `packages/react/src/toast/store.test.ts:7-8`) and bumped only when the internal update is called with `markUpdated` (`packages/react/src/toast/store.ts:249-251`). The public `updateToast` and the active-toast branch of `addToast` both pass `markUpdated: true` (`packages/react/src/toast/store.ts:177`, `packages/react/src/toast/store.ts:219-224`), which is exactly why upsert and update each advance the counter while internal-only writes (height recalculations) do not.
- Upsert of a toast that is already ending takes a third path: `removeToast(id, true)` with `skipOnRemove` so the old toast's `onRemove` never fires, then a fresh add (`packages/react/src/toast/store.ts:172-180`) — the mechanism behind "replacing an ending toast does not fire the old toast's onRemove" (part spec, "Events"). The upsert branch also strips `id` and `transitionStatus` from the caller's options before applying them (`packages/react/src/toast/store.ts:176`), which is why a caller-supplied `transitionStatus` is ignored (part spec, "State model").
- Re-entrancy is handled by re-reading state *after* the updater runs: `updateToast` evaluates the updater against the pre-update snapshot, then the internal update re-reads `this.state` (`packages/react/src/toast/store.ts:217-224`). That is why a toast added from inside an updater survives and lands before the updated toast in the array (`packages/react/src/toast/store.test.ts:157-167`), and why closing from inside an updater wins — the internal update then sees `transitionStatus: 'ending'` and bails, discarding the returned patch (`packages/react/src/toast/store.test.ts:169-178`).

### The timer state machine (outside React state entirely)

Auto-dismiss bookkeeping lives in a private `Map<string, TimerInfo>` on the store (`packages/react/src/toast/store.ts:100`, shape at `packages/react/src/toast/store.ts:518-527`), not in render state — timers must survive React re-renders and be shared across Provider/Viewport/Root. Each `TimerInfo` records `start`/`delay`/`remaining` so pause/resume can do wall-clock math:

- `scheduleTimer` (`packages/react/src/toast/store.ts:418-435`) decides whether the timeout actually runs based on `selectors.expandedOrOutOfFocus` (`packages/react/src/toast/store.ts:95`): when the viewport is expanded/hovered/focused or the window is blurred, only the bookkeeping entry is created (`timeout: undefined`) and no `setTimeout` starts. This is the mechanism behind "a rescheduled timer does not start while the viewport is expanded and runs once collapsed" (`packages/react/src/toast/store.test.ts:325-348`) and behind a newly added toast being paused immediately when the viewport is already expanded (`packages/react/src/toast/store.ts:198-200`).
- `pauseTimers` (`packages/react/src/toast/store.ts:364-380`) converts elapsed wall time into `remaining` by subtracting `Date.now() - start`, clamped at 0; `resumeTimers` (`packages/react/src/toast/store.ts:382-396`) restarts with `remaining`, falling back to the full `delay` when `remaining` is 0 — which is precisely the background-tab case: a wall-clock jump past the deadline clamps `remaining` to 0 at pause, so resume restarts the full delay (`packages/react/src/toast/store.test.ts:372-389`). Because `start` is restamped on every resume, subtracting from `remaining` (not from `delay`) keeps repeated pause/resume cycles from extending the toast's life (`packages/react/src/toast/store.test.ts:350-370`, `packages/react/src/toast/store.test.ts:407-426`).
- Timer reconciliation in `updateToastInternal` (`packages/react/src/toast/store.ts:256-285`): `shouldHaveTimer` requires non-ending, non-`loading`, positive timeout (`packages/react/src/toast/store.ts:261-262`); teardown happens when that flips false (`packages/react/src/toast/store.ts:268-271`), rescheduling when it is true *and* one of `!hasTimer || timeoutChanged || timeoutUpdated || wasLoading || resetTimer` holds (`packages/react/src/toast/store.ts:274-277`). The `timeoutUpdated` check is `Object.hasOwn(updates, 'timeout')` (`packages/react/src/toast/store.ts:259`) — key presence, not value change — which is what makes updating with the **same** timeout value reset the timer (part spec, "State model"), and `wasLoading` covers the loading→success transition where no timer ever existed (part spec, "State model"). `type: 'loading'` never gets a timer on add either (`packages/react/src/toast/store.ts:194-196`).
- The paused flag is *derived from liveness*, not tracked independently: both `clearTimer` and `handleTimerFired` delete the map entry and call `resetPausedStateIfNoTimersRemain` (`packages/react/src/toast/store.ts:445-456`), which flips `areTimersPaused` back to false once the map empties (`packages/react/src/toast/store.ts:458-464`). That single rule, plus `closeToast` clearing one timer (single id) or all of them (`close()`, `packages/react/src/toast/store.ts:289-303`), produces all four "re-pausable after the last toast goes away" scenarios (`packages/react/src/toast/store.test.ts:251-271`, `packages/react/src/toast/store.test.ts:273-288`, `packages/react/src/toast/store.test.ts:290-306`, `packages/react/src/toast/store.test.ts:308-323`) and the untimed-via-update variant (`packages/react/src/toast/store.test.ts:391-405`). The state-level half of the same cleanup is `setToasts`' `clearInteraction` flag, which resets `hovering`/`focused` when no active toast remains (`packages/react/src/toast/store.ts:305-311`, `packages/react/src/toast/store.ts:466-478`).

### Derived data: metadata and limited flags are recomputed, never patched

- `toastMetadata` (domIndex, visibleIndex, offsetY per id, `packages/react/src/toast/store.ts:37-42`) is a pure projection of `toasts`: `createToastMetadata` rebuilds the whole Map on every `setToasts` and on limit changes (`packages/react/src/toast/store.ts:131-135`, `packages/react/src/toast/store.ts:466-478`). `visibleIndex` is −1 for ending toasts so exit-animating toasts drop out of stack numbering while keeping their real `domIndex` (part spec, "State model" via `specs/library/toast/parts/shell.md` stacking). The store test's `expectToastMetadataToMatchToasts` (`packages/react/src/toast/store.test.ts:19-37`) is the executable statement of this invariant; the precomputed Map keeps the per-toast selectors (`packages/react/src/toast/store.ts:89-92`) O(1) at render time.
- `applyLimited` (`packages/react/src/toast/store.ts:74-84`) flags toasts beyond the limit in newest-first order and **returns the same object reference when the flag is unchanged** (`packages/react/src/toast/store.ts:82`). Reference stability is the mechanism behind "upserting a limited toast preserves its limited state" (part spec, "State model"): map-based updates (`packages/react/src/toast/store.ts:254`) and `applyLimited` both leave untouched toasts object-identical, so selector subscribers of other toasts don't re-render.
- `syncProviderProps` (`packages/react/src/toast/store.ts:119-138`) is the Provider-batch entry point: it no-ops when neither `timeout` nor `limit` changed and recomputes limited flags (via the full metadata rebuild) only when `limit` changed (`packages/react/src/toast/store.test.ts:229-243`).

### The promise machine

`promiseToast` (`packages/react/src/toast/store.ts:322-362`) composes the pieces above: add a `type: 'loading'` toast (no timer by the rule above), then chain `.then`/`.catch` that call `updateToast` with the resolved options plus the new `type` (`packages/react/src/toast/store.ts:333-353`). One load-bearing subtlety: the success/error update **always includes the `timeout` key, even when undefined** (`packages/react/src/toast/store.ts:339`, `packages/react/src/toast/store.ts:349`). Spreading `timeout: undefined` overwrites any toast-level timeout the loading state carried, so `nextTimeout` falls back to the provider default — the mechanism behind "a loading toast's timeout is not inherited by the success state" (part spec, "State model"); a `timeout: 0` from the state options flows through as `0` and disables auto-dismiss; and the always-present key trips the `timeoutUpdated` reschedule path. Option normalization (string → `{ description }`, function → called with the settled value, object → passed through) lives in `resolvePromiseOptions` (`packages/react/src/toast/utils/resolvePromiseOptions.ts:3-22`); `promiseToast` passes the resolved/rejected value as the function argument (`packages/react/src/toast/store.ts:335`, `packages/react/src/toast/store.ts:345`).

The external manager's `promise` returns the *handled* promise, not the input, through a synchronous handoff: `createToastManager.promise` seeds a local `handledPromise` with the raw input, emits a `promise` event carrying a `setPromise` closure that reassigns that local (`packages/react/src/toast/createToastManager.ts:64-82`), and since `emit` runs listeners synchronously, the store's `promiseToast` has already called `setPromise(handledPromise)` with its chained `.then/.catch` promise by the time `return handledPromise` executes. The store detects this private channel structurally — `{}.hasOwnProperty.call(options, 'setPromise')` (`packages/react/src/toast/store.ts:357-359`) — so any caller can omit it (the store-level tests do, `packages/react/src/toast/store.test.ts:206-215`).

### React hooks used (few by design)

`useToastManager` (`packages/react/src/toast/useToastManager.ts:9-24`) uses exactly two hooks: the context read (below) and `store.useState('toasts')` — the selector-keyed subscription of `ReactStore` (`packages/utils/src/store/ReactStore.ts:171-179`), which under the hood is `useSyncExternalStore` (raw on React 19+, shimmed otherwise, `packages/utils/src/store/useStore.ts:12-13`). Subscribing to the `toasts` array reference (not deep equality) is why `applyLimited`'s and the map-updates' reference preservation matters: unchanged toasts don't re-render their subscribers. The returned API object is memoized on `[toasts, store]` (`packages/react/src/toast/useToastManager.ts:14-23`), and since the store methods are stable instance properties, consumers may destructure and use them in effect deps safely. There is no `useState`/`useReducer`/`useRef` anywhere in the batch — all mutable state is either the store's or a plain closure.

### The two `.spec.tsx` files are type-check suites, not tests

Vitest excludes `**/*.spec.*` entirely (`vitest.shared.mts:51`); `packages/react/src/toast/createToastManager.spec.tsx` and `packages/react/src/toast/useToastManager.spec.tsx` are executed only by `tsc` (`pnpm typescript`). They pin the generic contract: `Data` defaults to `any` with per-call `T extends Data` overrides (`packages/react/src/toast/createToastManager.spec.tsx:71-103`), `add` returns `string` (`packages/react/src/toast/createToastManager.spec.tsx:18`), `data` replaces wholesale (the `@ts-expect-error` at `packages/react/src/toast/createToastManager.spec.tsx:44-49` documents that a partial `data` object is a type error), the updater receives the previous toast with `data?: Data | undefined` (`packages/react/src/toast/createToastManager.spec.tsx:51-54`), and function-valued `data` is a value, not an updater (`packages/react/src/toast/createToastManager.spec.tsx:105-121`). `useToastManager.spec.tsx` mirrors this for the hook — including that `toasts[0]?.data` is `Data | undefined` (`packages/react/src/toast/useToastManager.spec.tsx:10-13`) — and is the reason for the file-top `rules-of-hooks` disable: it calls the hook at module top level purely for type extraction, never in a component (`packages/react/src/toast/useToastManager.spec.tsx:1`, `packages/react/src/toast/useToastManager.spec.tsx:10`).

## Context providers/consumers

- One context, and its value **is the store**: `useToastProviderContext()` returns the `ToastStore` instance itself (`packages/react/src/toast/provider/ToastProviderContext.ts:5-7`), throwing the descriptive `Base UI:` error when called outside a Provider (`packages/react/src/toast/provider/ToastProviderContext.ts:9-14`) — the context-missing rejection behind "no Viewport mounted" and provider-less render failures (part spec, "Public API surface"). Shell batch, cited only.
- This batch provides no context of its own. The external-manager wiring is delegated entirely to the shell batch's Provider: it owns the `' subscribe'` listener that forwards `ToastManagerEvent`s into `store.addToast`/`closeToast`/`updateToast`/`promiseToast`, which is why both the controlled (external manager) and uncontrolled (default) modes of the part spec ("State model") collapse onto the same `ToastStore` methods the hook exposes.
- All other coordination in the unit (viewport expansion, root exit animations, positioner indices) flows through store state read via selectors, never through additional React contexts.

## DOM/portal strategy and why

This batch renders **no DOM and no portals** — it is the only toast batch with no `useRenderElement` call. Its DOM involvement is indirect, stored as data on the store so the components (other batches) can stay thin:

- The store holds the live viewport node via `setViewport` (`packages/react/src/toast/store.ts:115-117`), a ref callback the viewport batch attaches; store-side logic then does shadow-DOM-safe `contains()` tests against it — `handleDocumentPointerDown` (`packages/react/src/toast/store.ts:402-416`, touch-only, outside-viewport → resume timers + clear `hovering`/`focused`) and `handleFocusManagement` (`packages/react/src/toast/store.ts:480-515`).
- Focus management on close is a store concern for the same reason timers are: it must react to the *pre-close* state regardless of which component triggered the close. The algorithm (`packages/react/src/toast/store.ts:480-515`): do nothing unless focus-visible focus is inside the viewport (checked via `activeElement(ownerDocument(...))` + `isFocusVisible` + `contains`, `packages/react/src/toast/store.ts:481-488`); `close()` (no id) restores `prevFocusElement` (`packages/react/src/toast/store.ts:491-493`, via `restoreFocusToPrevElement` at `packages/react/src/toast/store.ts:398-400`); a single close scans forward then backward from the closing toast's index for the next non-ending toast and focuses its `toast.ref?.current` (`packages/react/src/toast/store.ts:498-514`). The toast `ref` field (`packages/react/src/toast/useToastManager.ts:33-34`) is the hand-off point: the root batch fills it with its rendered element, so the store can move focus without rendering anything itself.
- `height` on the toast object (`packages/react/src/toast/useToastManager.ts:75-77`) is written by the root batch's measurement and read only through metadata (`offsetY` accumulation, `packages/react/src/toast/store.ts:60`); the store itself zeroes it on close so the stack collapse is data-driven rather than DOM-measured.
- The metadata trio (`domIndex`, `visibleIndex`, `offsetY`) exists so the positioner/viewport batches can read per-toast layout integers from selectors instead of recomputing array walks during render.

## Anything in source not explained by any test

- **`handleFocusManagement` and `restoreFocusToPrevElement`** (`packages/react/src/toast/store.ts:480-515`, `packages/react/src/toast/store.ts:398-400`): the part spec marks manager-level focus behavior N/A — no test asserts focus movement or restoration; the only evidence in the batch's tests is the state shape (`focused`, `prevFocusElement` in `packages/react/src/toast/store.test.ts:12-15`). The forward-then-backward scan, the `preventScroll` restore, and the focus-visible gate are entirely test-uncovered here.
- **`handleDocumentPointerDown`** (`packages/react/src/toast/store.ts:402-416`): no batch test fires a touch pointerdown; its rules (touch-only, viewport containment, resume + interaction reset) are exercised, if at all, by the viewport batch that binds it (behavior spec, "Events").
- **`disposeEffect`** (`packages/react/src/toast/store.ts:140-147`): returns a cleanup that clears every timer; no test unmounts a provider (part spec, "Edge cases" — provider unmount UNVERIFIED), so this cleanup and its consumer in the shell batch are unproven.
- **Untested selectors**: `isEmpty`, `focused`, `expanded`, `expandedOrOutOfFocus`, `prevFocusElement` (`packages/react/src/toast/store.ts:88`, `packages/react/src/toast/store.ts:93-96`) are proven only indirectly through the timer-pause tests and are consumed by the viewport batch; `store.test.ts` asserts only the four toast-metadata selectors (part spec, "Public API surface").
- **`'animation'` in the add-options `Omit`** (`packages/react/src/toast/useToastManager.ts:124-127`): `ToastObject` has no `animation` key (`packages/react/src/toast/useToastManager.ts:26-97`), so the entry is a stale no-op — presumably a leftover from a removed field; nothing documents or tests it.
- **The manager's redundant `transitionStatus: 'starting'` stamp**: `createToastManager.add` pre-stamps it into the emitted options (`packages/react/src/toast/createToastManager.ts:31-35`) even though `store.addToast` stamps it again (`packages/react/src/toast/store.ts:187`). Redundant on the store path; only observable to a non-store `' subscribe'` listener, which no test installs.
- **`ToastManagerEvent.options: any`** (`packages/react/src/toast/createToastManager.ts:101-104`): the event channel is untyped end-to-end; neither type spec exercises the event shape, and the `update` action's `{ id, updates }` envelope (`packages/react/src/toast/createToastManager.ts:58-61`) is defined only by the Provider's consumption.
- **`generateId` format/collision surface** (`packages/utils/src/generateId.ts:1-4`): no test asserts the `toast-xxxx-N` shape or module-counter behavior; ids are treated as opaque.
- **Timer-fire ordering**: `scheduleTimer`/`resumeTimers` wrap callbacks as `handleTimerFired(id)` *then* the close callback (`packages/react/src/toast/store.ts:423-426`, `packages/react/src/toast/store.ts:390-393`), so the map entry is deleted before `closeToast` runs; the pause tests cover the outcomes but no test pins the ordering itself (e.g. a close callback that inspects `timers`).
