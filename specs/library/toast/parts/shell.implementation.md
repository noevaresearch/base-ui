# Toast shell — implementation spec (Provider + Portal + Positioner)

Implementation mined from source only. Evidence = the batch files `packages/react/src/toast/provider/ToastProvider.tsx`, `packages/react/src/toast/provider/ToastProviderContext.ts`, `packages/react/src/toast/portal/ToastPortal.tsx`, `packages/react/src/toast/positioner/ToastPositioner.tsx`, `packages/react/src/toast/positioner/ToastPositionerContext.ts`, `packages/react/src/toast/positioner/ToastPositionerCssVars.ts`, `packages/react/src/toast/positioner/ToastPositionerDataAttributes.ts`, plus the imports they pull in (cited per claim). This is the WHY/HOW companion to the behavior part (`specs/library/toast/parts/shell.md`); behavior claims are referenced by that file's section names, not restated. Store/manager internals (`store.ts`, `createToastManager.ts`, `useToastManager.ts`) belong to the manager batch and are only touched at the surface this batch consumes.

## State machine / hooks used

### Provider (`packages/react/src/toast/provider/ToastProvider.tsx`)

Hooks used, in render order:

- `useRefWithInit` (`packages/utils/src/useRefWithInit.ts:15-23`) — lazily constructs the `ToastStore` exactly once per component lifetime, at `packages/react/src/toast/provider/ToastProvider.tsx:18-30`, with the full initial state inlined (`viewport: null`, empty `toasts`, `hovering`/`focused`/`isWindowFocused` flags, `prevFocusElement: null`). The store is therefore always **internally owned**; there is no branch that substitutes a passed-in manager. `toastManager` never becomes the context value and never injects initial state — see below.
- `useOnMount` (`packages/utils/src/useOnMount.ts:8-12`, a `useEffect` with an empty dep array) running `store.disposeEffect` at `packages/react/src/toast/provider/ToastProvider.tsx:32`. The effect returns the cleanup defined in `packages/react/src/toast/store.ts:140-147`, which clears every toast timer on unmount.
- `React.useEffect` — the external-manager bridge at `packages/react/src/toast/provider/ToastProvider.tsx:34-57`, deps `[store, toastManager]`. When no `toastManager` prop is given it returns early (`packages/react/src/toast/provider/ToastProvider.tsx:36-38`); otherwise it subscribes to the manager's underscore-prefixed private channel `' subscribe'` (`packages/react/src/toast/createToastManager.ts:22-27`, typed at `packages/react/src/toast/createToastManager.ts:87`) and funnels each `{ action, options }` event into store methods: `promise` (only when `options.promise` is set) → `store.promiseToast` (`:43-44`), `update` with an `id` → `store.updateToast(id, options.updates)` (`:45-46`), `close` → `store.closeToast(id)` (`:47-48`; an undefined id means close-all in the store, `packages/react/src/toast/store.ts:288-295`), and everything else → `store.addToast(options)` (`:49-51`). The subscription's `unsubscribe` is returned as the effect cleanup (`:54`). The mapping is one-directional: imperative external calls (shell.md "External-manager mode") reach the store only through this bridge; the store never writes back to the manager. Note the store stays the single source of truth even in external-manager mode — the context value type is literally `ToastStore` (`packages/react/src/toast/provider/ToastProviderContext.ts:5`), so an external manager cannot be substituted, only observed.
- `useIsoLayoutEffect` (`packages/utils/src/useIsoLayoutEffect.ts:6`, `useLayoutEffect` on the client, no-op on the server) — but not in the Provider itself. Prop syncing lives in a dedicated child component, `ToastProviderPropsSynchronizer` (`packages/react/src/toast/provider/ToastProvider.tsx:67-81`), rendered as the **first child inside the context provider, before `children`** (`:61`), and rendering `null` (`:80`). Its single `useIsoLayoutEffect` (`:76-78`) calls `store.syncProviderProps(timeout, limit)` with deps `[store, timeout, limit]`.

Prop-sync semantics (`timeout`/`limit` → store), in three parts:

1. **Why a separate component instead of an effect on the Provider:** React invokes layout effects in completion order — a subtree completes before its parent, and earlier siblings complete before later sibling subtrees. Because the synchronizer is a leaf rendered ahead of `children` (`packages/react/src/toast/provider/ToastProvider.tsx:61`), its effect runs before any layout effect inside `children` in the same commit. This is the mechanism behind shell.md's "Same-commit prop + toast sync" and "Same-commit limit sync" edge cases: a descendant's `useIsoLayoutEffect` that calls `add()` in the same commit observes the freshly synced `timeout`/`limit`. Had the sync effect lived on the Provider itself, it would run *after* descendants' layout effects (parents complete last) and the same-commit add would see stale values.
2. **Why committed-render semantics:** layout effects only run when a render actually commits. An abandoned concurrent render — the `startTransition` + suspending-child case in shell.md's "Abandoned render isolation" — never reaches its layout effects, so `syncProviderProps` is never called with the discarded `timeout`/`limit` and the store keeps the last committed values.
3. **Why not `useSyncedValues`:** the source comment at `packages/react/src/toast/provider/ToastProvider.tsx:74-75` states it directly — `useSyncedValues` (the `ReactStore` generic prop-sync hook, `packages/utils/src/store/ReactStore.ts:90`) would only mirror the raw values, but a `limit` change must also recompute each toast's `limited` flag. `store.syncProviderProps` (`packages/react/src/toast/store.ts:119-138`) no-ops when `timeout` is unchanged and `limit` didn't change (`:122-124`), and on a `limit` change re-flags toasts and rebuilds `toastMetadata` (`:131-135`).

Provider defaults are destructured at `packages/react/src/toast/provider/ToastProvider.tsx:16`: `timeout = 5000`, `limit = 3` (documented at `:87-99`). These answer the defaults shell.md marks UNVERIFIED — source, not test, evidence.

The Provider renders no DOM and forwards no ref: it is a plain `React.FC` returning the context provider, the null-rendering synchronizer, and `children` (`packages/react/src/toast/provider/ToastProvider.tsx:59-64`); its state interface is empty (`:83`).

### Portal (`packages/react/src/toast/portal/ToastPortal.tsx`)

No state machine of its own — `React.forwardRef` delegating every prop (including `container`, typed `HTMLElement | ShadowRoot | RefObject<…> | null`, `packages/react/src/toast/portal/ToastPortal.tsx:22-28`) to `FloatingPortalLite` (`:13-18`). All mechanics live in the shared util (see "DOM/portal strategy and why").

### Positioner (`packages/react/src/toast/positioner/ToastPositioner.tsx`)

Hooks used, in render order:

- `useToastProviderContext()` at `packages/react/src/toast/positioner/ToastPositioner.tsx:33` — pulls the store from the Provider context (this is also where the out-of-context rejection of shell.md's "Out-of-context usage" originates, `packages/react/src/toast/provider/ToastProviderContext.ts:9-15`).
- `React.useState<HTMLDivElement | null>` at `:58` — holds the positioner's own DOM node, fed back into the floating machinery (see below).
- `store.useState('toastIndex', toast.id)` / `store.useState('toastVisibleIndex', toast.id)` at `:60-61`. `ReactStore.useState(key, ...args)` (`packages/utils/src/store/ReactStore.ts:171-178`) subscribes the component to a named selector with arguments; both selectors live in the store's selector table (`packages/react/src/toast/store.ts:90,92`) and fall back to `-1` when the id has no metadata.
- `useFloatingRootContext` (exported from `packages/react/src/floating-ui-react`, implemented at `packages/react/src/floating-ui-react/hooks/useFloatingRootContext.ts:26-80`) at `:65-72`, always configured with `open: true` and `onOpenChange: NOOP` (`NOOP` imported at `:15`), and `elements: { floating: positionerElement, reference: anchor }`. The hook keeps a `FloatingRootStore` and syncs the element refs into it from a layout effect (`packages/react/src/floating-ui-react/hooks/useFloatingRootContext.ts:58-74`).
- `useAnchorPositioning` (`packages/react/src/internals/useAnchorPositioning.ts`) at `:74-90`, with `mounted: true` and `keepMounted: true` — positioning runs permanently "open"; there is no open/close lifecycle in the positioning layer for toasts.
- `usePositioner` (`packages/react/src/utils/usePositioner.tsx:23-44`) at `:98-107` — the shared popup-positioner renderer, which wraps `useRenderElement('div', …)` (`packages/react/src/utils/usePositioner.tsx:34-43`).

**side/align/anchor resolution — element props vs `toast.positionerProps`:** `toast.positionerProps` is normalized once with an `EMPTY_OBJECT` fallback (`packages/react/src/toast/positioner/ToastPositioner.tsx:35-37`, `EMPTY_OBJECT` from `packages/utils/src/empty`). Then every positioning prop is destructured through a three-step fallback chain — element prop `??` `positionerProps.X` `??` hard default — for `anchor` (`:42`), `positionMethod` (`:43`, default `'absolute'`), `side` (`:44`, default `'top'`), `align` (`:45`, default `'center'`), `sideOffset`/`alignOffset` (`:46-47`, default `0`), `collisionBoundary` (`:48`, default `'clipping-ancestors'`), `collisionPadding`/`arrowPadding` (`:49-50`, default `5`), `sticky` (`:51`, default `false`), `disableAnchorTracking` (`:52`, default `false`), and `collisionAvoidance` (`:53`, default `POPUP_COLLISION_AVOIDANCE` = `{ fallbackAxisSide: 'end' }`, `packages/react/src/internals/constants.ts:26-28`). This destructuring *is* the precedence rule proven in shell.md's "State model" section: element props win, `positionerProps` fills gaps.

**Anchor:** `anchor = isElement(anchorProp) ? anchorProp : null` (`:63`, `isElement` from `@floating-ui/utils/dom`) — only real DOM elements survive; anything else (including null) yields an unanchored positioner, which still renders (shell.md "An unanchored toast still renders a positioner").

**State object:** `{ side: positioning.side, align: positioning.align, anchorHidden: positioning.anchorHidden }` (`:92-96`) — these are the *rendered* (collision-adjusted) values returned by `useAnchorPositioning` (`packages/react/src/internals/useAnchorPositioning.ts:814-822`, produced at `:611-612`), not the raw props. So `data-side`/`data-align` reflect where the toast actually ended up, and `anchorHidden` is the shared popup "anchor is hidden" state.

**`--toast-index` from store selectors:** the two selector reads (`:60-61`) map to metadata computed by `createToastMetadata` (`packages/react/src/toast/store.ts:46-68`): `domIndex` is the toast's array position (`:55`) and `visibleIndex` is a running counter that skips `transitionStatus === 'ending'` toasts and is `-1` for them (`:56`, `:62-64`). The style written at `:101-102` picks between them:

```
[ToastRootCssVars.index]: toast.transitionStatus === 'ending' ? domIndex : visibleIndex
```

where `ToastRootCssVars.index` is the string `'--toast-index'` (`packages/react/src/toast/root/ToastRootCssVars.ts:5`). Because the store inserts toasts newest-first (`packages/react/src/toast/store.ts:190`), a visible toast's `visibleIndex` is 0 for the newest and increases with age (shell.md "`--toast-index` transition"), while a *closing* toast switches to its `domIndex` — its real array slot, never `-1` — so it keeps a sensible index while animating out and the survivors re-index (shell.md "Close-while-animating").

**Element rendering:** `usePositioner(componentProps, state, { … })` at `:98-107` merges `positioning.positionerStyles` (the floating-engine styles, `packages/react/src/internals/useAnchorPositioning.ts:607`; these also carry the seeded `--available-width`/`--available-height` vars, `:526-527`) with the `--toast-index` var; passes `transitionStatus: toast.transitionStatus` (`:104`), which `usePositioner` converts into `transition: 'none'` while `'starting'` via `getDisabledMountTransitionStyles` (`packages/react/src/utils/usePositioner.tsx:39`, `packages/react/src/internals/getDisabledMountTransitionStyles.ts:8`, style constant `packages/react/src/internals/constants.ts:5`); and merges `refs: [forwardedRef, setPositionerElement]` (`:106`) so one ref serves the consumer and the other feeds `elements.floating` into the floating root context. `usePositioner` itself always applies `role: 'presentation'` (`packages/react/src/utils/usePositioner.tsx:38`) and maps state to attributes with `popupStateMapping` (`:42`).

**State → data attributes:** with state `{ side, align, anchorHidden }`, `popupStateMapping` (`packages/react/src/utils/popupStateMapping.ts:48-61`) intercepts only `anchorHidden` → `data-anchor-hidden` (`packages/react/src/utils/CommonPopupDataAttributes.ts:26`) — it also has an `open` handler (`:49-54`), but the Positioner state has no `open` key, so no `data-open`/`data-closed` is ever emitted, and `transitionStatus` is not in state at all, so no `data-starting-style`/`data-ending-style` either (the transition-aware mapping variant exists but is not used here, `packages/react/src/utils/popupStateMapping.ts:63-70`). `side`/`align` fall through to the generic state mapper, which emits `data-side`/`data-align` with the string value (`packages/react/src/internals/getStateAttributesProps.ts:24-28`) — the attributes asserted in shell.md's "DOM structure & portal behavior".

**Render:** the element is wrapped in `ToastPositionerContext.Provider value={positioning}` (`:109-111`); the full positioning object is a structural superset of the context's `Pick` type, so Arrow gets live values on every reposition.

## Context providers/consumers

- **`ToastProviderContext`** (`packages/react/src/toast/provider/ToastProviderContext.ts`): the context value is the `ToastStore` instance itself — `type ToastContext = ToastStore` (`:5`), `createContext<ToastContext | undefined>(undefined)` (`:7`). Provided at `packages/react/src/toast/provider/ToastProvider.tsx:60`. Consumers go through `useToastProviderContext()` (`:9-15`), which throws `'Base UI: useToastManager must be used within <Toast.Provider>.'` when absent (`:12`) — the error proven in shell.md's "Out-of-context usage". Consumers in the tree: `useToastManager` (`packages/react/src/toast/useToastManager.ts:10`, manager batch) and `ToastPositioner` (`packages/react/src/toast/positioner/ToastPositioner.tsx:33`). What crosses the boundary: the whole store — reactive state, selectors, and mutation methods (`addToast`/`updateToast`/`closeToast`/`promiseToast`, `syncProviderProps`, `setViewport`).
- **`ToastPositionerContext`** (`packages/react/src/toast/positioner/ToastPositionerContext.ts`): `Pick<UseAnchorPositioningReturnValue, 'side' | 'align' | 'arrowRef' | 'arrowUncentered' | 'arrowStyles'>` (`:5-8`), created with an `undefined` default (`:10-12`). Provided only by `ToastPositioner` (`packages/react/src/toast/positioner/ToastPositioner.tsx:110`). Its sole consumer is `Toast.Arrow` (`packages/react/src/toast/arrow/ToastArrow.tsx:3,20`), which reads rendered side/align and arrow geometry to style the arrow. The guard `useToastPositionerContext()` throws `'Base UI: ToastPositionerContext is missing. ToastPositioner parts must be placed within <Toast.Positioner>.'` (`packages/react/src/toast/positioner/ToastPositionerContext.ts:17-19`).
- **What each part consumes from ancestors:** Provider consumes nothing from ancestors (no context reads). Portal consumes nothing — it touches no context at all, which is why it works standalone in the conformance suite (shell.md "Portal conformance renders `<Toast.Portal />` standalone"). Positioner consumes the Provider context; inside `useFloatingPortalNode`/`useAnchorPositioning` it could see the shared floating `PortalContext`/`FloatingTree` contexts, but Toast supplies neither, so those read as absent.
- **What the Provider provides downward besides the store:** nothing else — no separate config context; `timeout`/`limit` reach descendants only via store state, synced by the synchronizer described above.

## DOM/portal strategy and why

- **Provider:** deliberately DOM-free. It renders only the context provider, a null-rendering sibling (the synchronizer), and `children` (`packages/react/src/toast/provider/ToastProvider.tsx:59-64,80`). No ref forwarding exists on this part, and its empty state interface (`:83`) means it never emits state attributes.
- **Portal:** a *two-level* portal built on `FloatingPortalLite` (`packages/react/src/utils/FloatingPortalLite.tsx:15-38`), chosen over the full `FloatingPortal` specifically because toasts need no tabbable/focus-guard machinery (`packages/react/src/utils/FloatingPortalLite.tsx:11-14`). Mechanics:
  1. `useFloatingPortalNode` (`packages/react/src/floating-ui-react/components/FloatingPortal.tsx:71-74`) renders the portal node itself as a real `div` via `useRenderElement`, carrying a `useId()`-generated `id` and a generated `data-*` portal attribute (`:51,127-136`).
  2. That node is mounted into the resolved container with `ReactDOM.createPortal(portalElement, containerElement)` (`:138-143`); `FloatingPortalLite` then portals the *children* into that node with a second `createPortal(children, portalNode)` (`packages/react/src/utils/FloatingPortalLite.tsx:32-37`).
  3. Container resolution (`packages/react/src/floating-ui-react/components/FloatingPortal.tsx:95-125`): explicit node/ref → parent portal node from the shared `PortalContext` (`:77-78,106-109`) → `document.body`. An explicitly passed `container={null}` tears the portal down (`:97-104`), and `FloatingPortalLite` renders `null` when there is neither subtree nor node (`packages/react/src/utils/FloatingPortalLite.tsx:28-30`).
  4. The forwarded ref lands on the portal node div through the merged ref list `[ref, setPortalNodeRef]` (`packages/react/src/floating-ui-react/components/FloatingPortal.tsx:128`) — this is what the ref conformance suite observes even though `<Toast.Portal />` renders standalone with no children (shell.md "DOM structure & portal behavior").
  Note: the parent-portal nesting path is unreachable through `Toast.Portal` — `FloatingPortalLite` never publishes the `PortalContext` that would make a nested portal resolve to its parent, so every Toast portal independently resolves to `document.body` or the explicit `container`.
  Per shell.md, container/stacking/reparenting behavior is UNVERIFIED by tests; the two-level portal shape (container → portal div → viewport subtree) is exactly the kind of detail the golden-fixture stage must encode.
- **Positioner:** always renders a `div` (role `presentation`) that registers itself as the floating element via `setPositionerElement`; positioning is perpetual (`mounted: true`, `keepMounted: true`, `open: true`) because toasts are long-lived stacked elements, not transient popups. The anchor may be `null` (unanchored toasts) — the floating context still forms, just with a null reference, so the element renders with default placement `top`/`center` (shell.md "Positioner defaults"). `positionMethod` defaults to `'absolute'` (`:43`), and until the first positioning pass the styles hold `position` at the resolved method with zeroed coordinates and `opacity: 0`, plus seeded `--available-width`/`--available-height` fallbacks (`packages/react/src/internals/useAnchorPositioning.ts:500-531`) — the anti-flash/anti-zoom behavior for the browser-only geometry test in shell.md.
