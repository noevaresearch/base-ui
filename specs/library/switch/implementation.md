## State machine / hooks used

The component has no reducer. Its "state machine" is a single controlled boolean (`checked`) plus inherited Field lifecycle state (touched/dirty/filled/focused/valid) that is not owned here at all — it comes from `FieldRootContext` (next section). Every user interaction converges on one transition funnel: the hidden native checkbox's `onChange`.

Hooks and their call sites (in `packages/react/src/switch/root/SwitchRoot.tsx` unless noted):

- `useControlled` (`packages/react/src/switch/root/SwitchRoot.tsx:86-91`) — the one source of truth for `checked`. The `Boolean(defaultChecked)` coercion (`packages/react/src/switch/root/SwitchRoot.tsx:88`) is why the uncontrolled default is unchecked (behavior.md → "State model"). Internals: the mode is fixed on first render via a ref (`packages/utils/src/useControlled.ts:41`), `setCheckedState` silently no-ops in controlled mode (`packages/utils/src/useControlled.ts:82-89`), and dev-only warnings cover mode/default flipping (`packages/utils/src/useControlled.ts:47-80`).
- **Single funnel.** `setCheckedState` is called from exactly one place, the hidden input's `onChange` (`packages/react/src/switch/root/SwitchRoot.tsx:192`). Root clicks never set state: root `onClick` synthesizes a click on the input (`packages/react/src/switch/root/SwitchRoot.tsx:155`), the browser performs the native toggle, and the change event lands in `onChange`. Keyboard never sets state either: `useButton`'s Enter/Space handlers synthesize the same click (`packages/react/src/internals/use-button/useButton.ts:172-175` for Enter keydown, `packages/react/src/internals/use-button/useButton.ts:207-216` for Space keyup in non-native mode). A direct hidden-input click also funnels through natively.
- **Veto protocol.** `createChangeEventDetails(REASONS.none, event.nativeEvent)` (`packages/react/src/switch/root/SwitchRoot.tsx:184`), `onCheckedChange?.(nextChecked, eventDetails)` (`packages/react/src/switch/root/SwitchRoot.tsx:186`), then `eventDetails.isCanceled` short-circuits before `setCheckedState` (`packages/react/src/switch/root/SwitchRoot.tsx:188-192`). Because the input is React-controlled (`checked` at `packages/react/src/switch/root/SwitchRoot.tsx:161`), a cancel also lets React's controlled-input restoration flip the input's DOM checkedness back — the mechanism behind behavior.md → "State model" (`cancel()` leaves both `aria-checked` and the input unchecked and suppresses `data-dirty`/`data-filled`: neither `useValueChanged` nor `setFilled`'s effect sees a state change).
- **Guard layers on the funnel.** A change arriving with a default-prevented native event is ignored (React #9023 workaround, `packages/react/src/switch/root/SwitchRoot.tsx:172-176` — behavior.md → "Events" canceled hidden-input click); `readOnly` re-preventDefaults and bails there too (`packages/react/src/switch/root/SwitchRoot.tsx:178-181`), so direct input clicks are covered, not just root clicks; root `onClick` additionally guards `readOnly || disabled` (`packages/react/src/switch/root/SwitchRoot.tsx:143-146`).
- `useButton({ disabled, native: nativeButton })` (`packages/react/src/switch/root/SwitchRoot.tsx:106-109`) — centralizes the native-vs-non-native duality (default `nativeButton = false`, `packages/react/src/switch/root/SwitchRoot.tsx:46`). For the default span, `getButtonProps` supplies a `role="button"` fallback (`packages/react/src/internals/use-button/useButton.ts:226`) and keyboard activation: Enter dispatches a click on keydown and Space on keyup (`packages/react/src/internals/use-button/useButton.ts:172-175`, `packages/react/src/internals/use-button/useButton.ts:207-216`) — behavior.md → "Keyboard interactions" (both keys toggle). With a native `<button>`, the keyboard block early-returns (`packages/react/src/internals/use-button/useButton.ts:155-163`) and native activation takes over (behavior.md's `nativeButton` rows). Disabled handling — click/pointer/key guards (`packages/react/src/internals/use-button/useButton.ts:104-110`, `packages/react/src/internals/use-button/useButton.ts:218-224`) — and the `aria-disabled`/`tabIndex` wiring come from `useFocusableWhenDisabled` (`packages/react/src/internals/use-button/useButton.ts:28-34`; `packages/react/src/utils/useFocusableWhenDisabled.ts:33-47` adds `aria-disabled` when a non-native element is disabled and the `disabled` attribute on native buttons; `packages/react/src/utils/useFocusableWhenDisabled.ts:30-36` keeps the span tabbable until disabled) — behavior.md → "Accessibility" (`aria-disabled` instead of the disabled attribute).
- **Merge-order note** (why the roles compose): `useRenderElement` merges its `props` array left-to-right, and props-getter functions receive the accumulated props (`packages/react/src/merge-props/mergeProps.ts:126-131`, `packages/react/src/merge-props/mergeProps.ts:210-219`), merging their internals *beneath* them. So `role: 'switch'` (`packages/react/src/switch/root/SwitchRoot.tsx:120`) survives `useButton`'s `role: 'button'` fallback, and a consumer-supplied `role` (in `elementProps`) survives both via plain overwrite (`packages/react/src/merge-props/mergeProps.ts:177-182`) — behavior.md → "Accessibility" role override.
- `useIsoLayoutEffect` (`packages/react/src/switch/root/SwitchRoot.tsx:95-97`) — pushes `setFilled(checked)` into the Field on every commit including mount: the mechanism behind behavior.md → "State model" (filled added when checked, present initially with `defaultChecked`, cleared on remount).
- `useValueChanged` (`packages/react/src/switch/root/SwitchRoot.tsx:99-104`) — layout-effect diff firing only on real changes, never on mount (`packages/react/src/internals/useValueChanged.ts:10-16`): `clearErrors(name)` (`packages/react/src/switch/root/SwitchRoot.tsx:100`), `setDirty(checked !== validityData.initialValue)` (`packages/react/src/switch/root/SwitchRoot.tsx:101`), `validation.change(checked)` (`packages/react/src/switch/root/SwitchRoot.tsx:103`). Because it reacts to the value rather than the gesture, externally driven controlled changes also re-run validation while a user change validates exactly once (behavior.md → "Edge cases").
- `useRegisterFieldControl(switchRef, id, checked, undefined, !disabled, nameProp)` (`packages/react/src/switch/root/SwitchRoot.tsx:93`) — registers the switch as a Field control carrying the live `checked`; disabled switches deregister. Re-registration updates the form's fields map in place on value change rather than delete + re-add (`packages/react/src/internals/field-register-control/useRegisterFieldControl.ts:18-38`).
- **Ref plumbing.** `useMergedRefs(inputRef, externalInputRef, validation.inputRef)` (`packages/react/src/switch/root/SwitchRoot.tsx:76-77`) combines the internal ref, the consumer's `inputRef`, and Field validation registration; the element refs are `[forwardedRef, switchRef, buttonRef]` (`packages/react/src/switch/root/SwitchRoot.tsx:220`); `switchRef` (`packages/react/src/switch/root/SwitchRoot.tsx:79`) backs focus forwarding.
- **Ids — two lanes.** `useBaseUiId` (`packages/react/src/switch/root/SwitchRoot.tsx:81`) generates the `base-ui-`-prefixed instance id (`packages/react/src/internals/useBaseUiId.ts:9-11`) for the visible element in non-native mode; `useLabelableId({ id: idProp })` (`packages/react/src/switch/root/SwitchRoot.tsx:83`) resolves the labelable control id with Field-provider precedence (`packages/react/src/internals/labelable-provider/useLabelableId.ts:82`). The lanes split at `packages/react/src/switch/root/SwitchRoot.tsx:84` (`hiddenInputId = nativeButton ? undefined : controlId`) and `packages/react/src/switch/root/SwitchRoot.tsx:119` (`id: nativeButton ? controlId : id`): non-native → control id on the hidden input, internal id on the visible span; `nativeButton` → control id on the visible element, none on the input. This single split is behavior.md → "Accessibility" label-`for` targeting and the nativeButton id placement.
- `useAriaLabelledBy(ariaLabelledByProp, labelId, inputRef, !nativeButton, hiddenInputId)` (`packages/react/src/switch/root/SwitchRoot.tsx:110-116`) — precedence: explicit prop > Field label id > DOM-discovered fallback. The fallback (disabled in nativeButton mode, `packages/react/src/switch/root/SwitchRoot.tsx:114`) traverses from the hidden input — parent-label fast path, sibling `label[for]`, then `.labels` (`packages/react/src/internals/labelable-provider/useAriaLabelledBy.ts:49-70`) — and assigns an id-less label a generated `${hiddenInputId}-label` id (`packages/react/src/internals/labelable-provider/useAriaLabelledBy.ts:15`, `packages/react/src/internals/labelable-provider/useAriaLabelledBy.ts:42-44`); it re-runs after every commit with no dep array (`packages/react/src/internals/labelable-provider/useAriaLabelledBy.ts:22-31`) so label mount/unmount and id changes are picked up. This produces behavior.md → "Accessibility" label linking.
- State memo (`packages/react/src/switch/root/SwitchRoot.tsx:207-216`) — `{ ...fieldState, checked, disabled, readOnly, required }`: one object feeding both the data-attribute pipeline and the context, which is why Root and Thumb always agree.

State → attribute pipeline: `stateAttributesMapping` (`packages/react/src/switch/stateAttributesMapping.ts:6-15`) spreads `fieldValidityMapping` (`packages/react/src/internals/field-constants/constants.ts:34-43`: `valid: true → data-valid`, `false → data-invalid`, `null → nothing`) and customizes only `checked` into the mutually exclusive `data-checked`/`data-unchecked` pair (`packages/react/src/switch/stateAttributesMapping.ts:8-14`). Everything else is generic: truthy booleans emit `data-<key>` (`packages/react/src/internals/getStateAttributesProps.ts:24-28`), producing data-disabled/readonly/required/touched/dirty/filled/focused. Attribute constants live in `packages/react/src/switch/root/SwitchRootDataAttributes.ts:1-44`, mirrored verbatim for the thumb in `packages/react/src/switch/thumb/SwitchThumbDataAttributes.ts:1-44`.

## Context providers/consumers

**Provided:** `SwitchRootContext.Provider value={state}` wraps the rendered element and both inputs (`packages/react/src/switch/root/SwitchRoot.tsx:230-238`). The context type is nothing more than the state snapshot (`packages/react/src/switch/root/SwitchRootContext.ts:5-7`) — read-only state, no setters or refs — so consumers can react to state but cannot mutate it; all interaction handlers live on Root. The only consumer is `SwitchThumb` via `useSwitchRootContext()` (`packages/react/src/switch/thumb/SwitchThumb.tsx:21`), which throws `Base UI: SwitchRootContext is missing. Switch parts must be placed within <Switch.Root>.` when undefined (`packages/react/src/switch/root/SwitchRootContext.ts:9-18`) — the rejection asserted in behavior.md → "Public API surface". The thumb renders a `span` from that state with the same `stateAttributesMapping` (`packages/react/src/switch/thumb/SwitchThumb.tsx:23-28`): the "thumb receives the same data-* state hooks as the root" claim in behavior.md → "DOM structure & portal behavior" is structural (shared state object + shared mapping), not duplicated logic.

**Consumed** (Root only; the thumb consumes nothing but its own props — all Field/Form/Labelable integration lives in Root, which composes rather than reimplements):

- `useFormContext()` → `clearErrors` (`packages/react/src/switch/root/SwitchRoot.tsx:58`): checked-value changes clear the field's errors (invoked from `useValueChanged`, `packages/react/src/switch/root/SwitchRoot.tsx:100`).
- `useFieldRootContext()` (`packages/react/src/switch/root/SwitchRoot.tsx:59-70`): Field `disabled`/`name` merges (`disabled = fieldDisabled || disabledProp` at `packages/react/src/switch/root/SwitchRoot.tsx:73`, `name = fieldName ?? nameProp` at `packages/react/src/switch/root/SwitchRoot.tsx:74` — behavior.md → "State model" Field-disabled inheritance), the lifecycle setters (`setTouched`/`setDirty`/`setFilled`/`setFocused`), `validityData` (the dirty-comparison baseline), `validationMode`, `fieldState` (spread into the state object at `packages/react/src/switch/root/SwitchRoot.tsx:209` — the origin of every `data-touched`/`data-dirty`/`data-filled`/`data-focused`/`data-valid` hook), and `validation` (`inputRef` registration, `getValidationProps`, `change`/`commit`). Outside a `Field.Root` every one of these degrades to no-ops/defaults (`packages/react/src/internals/field-root-context/FieldRootContext.ts:32-61`), which is why behavior.md marks the Field hooks "when wrapped in Field.Root".
- `useLabelableContext()` → `labelId` (`packages/react/src/switch/root/SwitchRoot.tsx:71`): the Field.Label id feeding the `aria-labelledby` precedence chain (`packages/react/src/switch/root/SwitchRoot.tsx:110-116`; behavior.md → "Accessibility" Field.Label associations).
- Indirect, via `useButton`: the composite-root context (`packages/react/src/internals/use-button/useButton.ts:25`) — inside a Composite/Toolbar the switch becomes a composite item, changing Space activation timing to keydown (`packages/react/src/internals/use-button/useButton.ts:138-152`). No switch test exercises this fork.

## DOM/portal strategy and why

No portals exist anywhere in the unit; all DOM renders inline (consistent with behavior.md → "DOM structure & portal behavior", which records no portal assertions). The Root returns three siblings inside the provider (`packages/react/src/switch/root/SwitchRoot.tsx:230-238`):

1. The visible styled element from `useRenderElement('span', …)` (`packages/react/src/switch/root/SwitchRoot.tsx:218-228`): `role="switch"`, `aria-checked`, `aria-readonly`/`aria-required` (via `|| undefined` at `packages/react/src/switch/root/SwitchRoot.tsx:122-123`, so they are absent when unset), the merged `aria-labelledby`, and focus/blur/click handlers (`rootProps`, `packages/react/src/switch/root/SwitchRoot.tsx:118-157`). `onFocus` sets focused only when not disabled (`packages/react/src/switch/root/SwitchRoot.tsx:125-129`); `onBlur` marks touched, clears focused, and commits validation when `validationMode === 'onBlur'` using the input's live checkedness (`packages/react/src/switch/root/SwitchRoot.tsx:130-142`) — the mechanisms behind behavior.md → "Focus management" and onBlur validation.
2. A conditional `<input type="hidden">` for `uncheckedValue` (`packages/react/src/switch/root/SwitchRoot.tsx:233-235`), rendered only while `!checked && name && uncheckedValue !== undefined`, mirroring `form`/`disabled`. Why: hidden inputs always submit, so this is how an *off* switch submits a payload while the real checkbox submits nothing when unchecked (native semantics — behavior.md → "Events" FormData rules; the disabled mirror withholds the off value for disabled switches).
3. The visually hidden native `<input type="checkbox">` (props at `packages/react/src/switch/root/SwitchRoot.tsx:159-205`, rendered at `packages/react/src/switch/root/SwitchRoot.tsx:236` with `suppressHydrationWarning`): `checked`/`disabled`/`form`/`id`/`name`/`required`/`type` (`packages/react/src/switch/root/SwitchRoot.tsx:161-171`), `tabIndex: -1` + `aria-hidden: true` (`packages/react/src/switch/root/SwitchRoot.tsx:168-170`), `style: name ? visuallyHiddenInput : visuallyHidden` (`packages/react/src/switch/root/SwitchRoot.tsx:167`), and the React <19 conditional `value` spread (`packages/react/src/switch/root/SwitchRoot.tsx:202-204`).

Why this split:

- **The native input is the form engine.** FormData participation, native `required`/`valueMissing` validation, and external-form association via `form` are inherited rather than reimplemented — behavior.md → "Events" (submission follows native checkbox semantics, `value`/`uncheckedValue` customization) and → "Accessibility" (native HTML validation surfaces through `Field.Error`). `name`/`value` exist only here, never on the root.
- **The visible span is the a11y/focus surface.** The input is untabbable and aria-hidden; its `onFocus` forwards focus to the switch (`packages/react/src/switch/root/SwitchRoot.tsx:199-201`) so label-driven focus lands on the styled element, and Tab reaches the span (behavior.md → "Keyboard interactions").
- **Toggling re-dispatches a click onto the input instead of setting state directly.** Root `onClick` guards `readOnly || disabled` (`packages/react/src/switch/root/SwitchRoot.tsx:144-146`), `preventDefault()`s the original click (`packages/react/src/switch/root/SwitchRoot.tsx:148`) so a rendered real button cannot fire a competing native activation, then `dispatchClickWithModifiers(input, event)` (`packages/react/src/switch/root/SwitchRoot.tsx:155`) — an untrusted, bubbling, composed click carrying the source event's modifier keys (`packages/react/src/utils/dispatchClickWithModifiers.ts:19-36`). The browser performs the real toggle, and `onChange` is the single funnel. Three behavior.md → "Events" observations fall out structurally: exactly one ancestor click per gesture (the input's own `onClick` stops propagation because the re-dispatch is an implementation detail, `packages/react/src/switch/root/SwitchRoot.tsx:194-198`), `eventDetails.event.shiftKey` works (modifiers are forwarded), and a click canceled before React handles it is ignored via the `nativeEvent.defaultPrevented` check (`packages/react/src/switch/root/SwitchRoot.tsx:172-176`).
- **`nativeButton` mode** (`render={<button/>}` + `nativeButton`): `getButtonProps` adds `type="button"` (`packages/react/src/internals/use-button/useButton.ts:226`), Enter/Space activation is native (early return, `packages/react/src/internals/use-button/useButton.ts:155-163`), the label fallback is disabled (`packages/react/src/switch/root/SwitchRoot.tsx:114`) because there is no id-carrying labelable input to discover, and Field.Label/explicit `aria-labelledby` still work — behavior.md → "DOM structure" (the button is the same `role="switch"` node).
- `validation.getValidationProps(disabled, props)` is applied last on the root (`packages/react/src/switch/root/SwitchRoot.tsx:225`) and spread onto the input (`packages/react/src/switch/root/SwitchRoot.tsx:160`): Field-owned validation attributes (`aria-invalid` etc.); it is an identity pass-through outside a Field (`packages/react/src/internals/field-root-context/FieldRootContext.ts:53`).

Public surface assembly is trivial: `packages/react/src/switch/index.parts.ts:1-2` aliases `Root`/`Thumb`, and `packages/react/src/switch/index.ts:1-4` exports the `Switch` namespace plus types.

## Anything in source not explained by any test

Flagged explicitly for the golden-fixture stage and the backward-looking audit; none of these are silently dropped:

1. **`data-valid`/`data-invalid` never asserted.** The mapping exists (`packages/react/src/switch/stateAttributesMapping.ts:7` via `fieldValidityMapping`) and `valid` is in the state, but switch tests assert only `aria-invalid`; no test in this unit checks the `data-valid`/`data-invalid` attributes (in contrast to `data-checked`/`data-unchecked`/`data-readonly`/`data-required`, which are asserted at `packages/react/src/switch/root/SwitchRoot.test.tsx:422-439` — a behavior.md coverage note as much as a source gap).
2. **Composite-item integration.** Inside a Composite root, `useButton` flips Space to keydown activation (`packages/react/src/internals/use-button/useButton.ts:138-152`); no switch test renders the switch inside a Composite/Toolbar, so this behavioral fork is unverified.
3. **Hidden-input disabled mirroring.** The checkbox receives `disabled` (`packages/react/src/switch/root/SwitchRoot.tsx:162`) and so does the off-value hidden input (`packages/react/src/switch/root/SwitchRoot.tsx:234`); jsdom tests never assert these attributes directly — only the browser-only submission consequence is tested (behavior.md → "Events", Chromium-gated).
4. **`suppressHydrationWarning`** on the checkbox (`packages/react/src/switch/root/SwitchRoot.tsx:236`): SSR/hydration tolerance with no SSR test in this unit.
5. **The two visually-hidden style modes.** `name ? visuallyHiddenInput : visuallyHidden` (`packages/react/src/switch/root/SwitchRoot.tsx:167`) switches the input's hiding strategy on form participation; every test only observes that the input is hidden.
6. **Hidden-input focus forwarding.** The input's `onFocus` → `switchRef.current?.focus()` (`packages/react/src/switch/root/SwitchRoot.tsx:199-201`) is never directly asserted; behavior.md's focus tests drive Tab on the visible control and its label tests assert toggling, not where focus lands.
7. **Field-control re-registration on toggle.** `useRegisterFieldControl` receives the live `checked` (`packages/react/src/switch/root/SwitchRoot.tsx:93`), so its in-place re-registration on every toggle (`packages/react/src/internals/field-register-control/useRegisterFieldControl.ts:18-38`) has effects observable only from Form-side code, outside this unit.
8. **React <19 conditional `value` spread** (`packages/react/src/switch/root/SwitchRoot.tsx:202-204`): the workaround is unasserted; only the outcome (no `value` attribute without the prop, behavior.md → "State model") is tested.
9. **Dev-only `useButton` element-type warnings** (`packages/react/src/internals/use-button/useButton.ts:36-66`): mismatch diagnostics for `nativeButton` vs the rendered tag; no switch test asserts them.
10. **Synthesized clicks keep `detail` 0.** `dispatchClickWithModifiers` defaults `detail` to 0 (the keyboard convention) and switch never passes `detail: 1` even for mouse-originated clicks (`packages/react/src/switch/root/SwitchRoot.tsx:155`); the option exists for consumers keying off `detail === 0` (`packages/react/src/utils/dispatchClickWithModifiers.ts:17`) but no switch behavior depends on it — untested surface shared with the checkbox-style funnel.

Explained-but-worth-noting (not gaps): `REASONS.none` is the only change reason the switch ever emits (`packages/react/src/switch/root/SwitchRoot.tsx:184`), so behavior.md records no reason taxonomy for it; `aria-readonly`/`aria-required` use `|| undefined` (`packages/react/src/switch/root/SwitchRoot.tsx:122-123`), which is exactly why they are absent when unset (behavior.md → "Accessibility"); the `allowPropagation`/`trigger` fields of the change-event details (`packages/react/src/internals/createBaseUIEventDetails.ts:70-84`) are part of the generic details shape and go unused by switch.
